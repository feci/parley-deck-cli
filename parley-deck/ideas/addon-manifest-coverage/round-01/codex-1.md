## Summary

I reproduced the reported six-skill foreign-copy case: `doctor` exited 1, with only `parley-bidding` classified `valid-unmanaged`. In a temporary package copy, adding manifests to the other five skill directories made all five add-ons `valid-unmanaged`, but the core remained `malformed` because `unmanagedButVerified` still had no core source anchor. I recommend committed, generated manifests for all six units plus a generic unit-level packaged-source/proof model; I do not recommend weakening the unmarked-tree classification or changing the exit-code policy. I also reproduced a stronger B3 concern: the four currently manifest-free add-ons, installed natively and then gutted to `SKILL.md` while retaining their marker, still report `valid`, so full manifest coverage closes an existing false green as well as the foreign-installer false red.

## Proposed approach

1. **Choose manifest coverage plus a generic source anchor; retain the existing status and exit semantics.** Every directory under `skills/` that contains `SKILL.md`, including `skills/parley-deck`, should ship `parley-addon.json`. Each constructed unit should carry an explicit `sourceRoot` (or equivalently named proof descriptor): for current units it is `path.join(packageRoot, "skills", unit.skill)`. Add-ons discovered from an older marker but no longer shipped may have no source root and therefore cannot qualify as verified unmanaged. `unmanagedButVerified` should consume this property, never `unit.addon` and never a skill-name branch.

   The proof remains the narrow one already established for bidding: the packaged source manifest must exist and verify; the installed manifest bytes must equal the applicable packaged-source-derived manifest; and the installed payload must match exactly. A semantic shortcut such as “unmarked plus required files means valid-unmanaged” leaves the B3 hole open, because most units' required-file check is only `SKILL.md`. An exit-code-only change leaves every malformed classification in place and merely hides real gutted or modified trees from automation. Manifests without the generic anchor fix the add-ons but leave the core false red; I reproduced exactly that result.

2. **Make the unit proof model cover install, status, and doctor without granting ownership.** Replace source-integrity tests based on `unit.addon && hasManifest(unit.addon.root)` with the generic source proof in preflight, staging validation, marker creation, and health validation. A native install should record the manifest aggregate and manifest-file hash for every unit, not only add-ons, so a marker-present gutted tree cannot fall back to a `SKILL.md` check. `status` and `doctor` already share `skillUnitStatus`; they should continue to return the same per-unit status. Install and uninstall must continue to use `installerOwnsDestination`, so a verified foreign tree is healthy but unowned: without `--force`, install does not replace it, uninstall does not remove it, and neither command synthesizes a marker. Explicit `--force` remains the ownership-changing operation.

3. **Anchor the core at its canonical skill directory, while accounting for its native target projections exactly.** The correct canonical source anchor is `packageRoot/skills/parley-deck`, not the repository root and not the installed destination. The core is unusual only in copying: the native installer currently assembles it from that directory plus root-level metadata and optional files, with Antigravity/Gemini transformations. That must not lead to a verifier that ignores unexpected files, because doing so would weaken the current manifest semantics.

   I would model an exact expected payload layout as data on each unit. Identity-copied skills have one layout derived from their committed source manifest. The core has the canonical identity layout used by a universal installer and, where native target scaffolding cannot be normalized away, an exact target layout deterministically derived from the existing copy plan and packaged bytes. A staged native core manifest can be computed only after those deterministic transformations, but an unmarked installed copy qualifies only if that manifest and full file set equal a layout recomputed from the packaged source. This supports both a verbatim universal copy and native Gemini/Antigravity layouts without allowing arbitrary extras or trusting the installed manifest as its own authority. The verifier remains generic: it evaluates unit-supplied source-backed layouts rather than naming `parley-deck`.

4. **Commit generated manifests; do not create them only at pack time.** Pack-time-only generation would not help the README's first path, which installs directly from the repository's skill directories, and it would let GitHub, npm, portable, Homebrew, and WinGet carry different proof bytes. Extend `scripts/build-addon-manifest.js` so its inventory is every `skills/*/SKILL.md` directory, including the core; an omitted manifest is a `--check` failure rather than an opt-out. Keep the manifests committed and deterministically regenerated, while `npm test`, `prepack`, portable builds, and the release workflow run check-only verification.

   This changes stale-manifest failure from a downstream surprise into a source/release failure. `--check` must byte-compare the recomputed manifest, and install preflight must verify every source manifest before any fleet write. Thus a dirty developer tree with a stale manifest fails loudly before installation, while CI and prepack prevent that state from entering any release channel. Automatic regeneration during prepack is undesirable because it can conceal an uncommitted payload change and make one channel differ from the repository channel.

5. **Keep `valid-unmanaged` and the current doctor gate.** It is the right terminal status for a foreign-installed tree that is byte-proven against this package's source: integrity is healthy, provenance/ownership is absent. `managed: false` and `marker: null` preserve the distinction for automation. `doctor` should exit 0 when every selected unit is `valid` or `valid-unmanaged` **and** every declared runtime requirement is available; it should not let an integrity verdict mask an unavailable interpreter. This policy is already implemented: I reproduced an exit-0 run containing a managed core and an unmarked, source-verified `parley-bidding`. The observed exit 1 therefore needs coverage and anchoring fixes, not an exit-policy change.

6. **Add regressions that prove the transition and B3 together.** The primary regression should be a table-driven test such as `foreign copies are accepted only when complete` over all six units. For each unit, its first subtest copies the packaged skill directory verbatim with no marker and asserts `valid-unmanaged`, `managed: false`, `marker: null`, matching `status` output, and a doctor exit of 0 with a controlled Python 3.10+ stub. Its second subtest replaces that tree with only `SKILL.md` and asserts `malformed` plus doctor exit 1. The full-copy arm fails on five units at the current commit, so this is a genuine regression for the proposed change while the paired negative arm proves the unmarked B3 invariant.

   Add a second table-driven B3 regression for marker-present trees: install all six natively, retain `SKILL.md` and the marker, delete everything else, and assert every unit is `malformed`. This currently fails for `parley-design`, `parley-design-check`, `parley-tracker`, and `parley-worktrees`, which I reproduced as an overall doctor exit 0. Add source-drift regressions for both an identity add-on and the core: modify a packaged payload without regenerating its manifest, assert manifest `--check` fails, assert install preflight writes no destination, then regenerate and assert native install/doctor succeeds. Finally, extend the existing ownership regression from bidding to all six: a `valid-unmanaged` fleet blocks install and uninstall without `--force`, remains untouched and unmarked, and can be explicitly reclaimed or removed with `--force`. Gemini and Antigravity core tests must exercise their transformed exact layouts so a core-only success on Codex cannot hide a target-projection defect.

   Documentation and release acceptance should remove the README/CHANGELOG claim that bidding is the only externally verifiable skill, verify all six manifests are present in packaged inventories, bump the version, and exercise all five release channels.

## Concerns / open questions

- The core's assembled native layout is the main implementation hazard. Before coding, confirm whether ordinary targets can stop receiving unrelated root-level `README.md`, `LICENSE`, `plugin.json`, and `gemini-extension.json`. Fewer layouts are preferable, but Gemini and Antigravity behavior must be measured rather than assumed. If projections remain, they must be exact source-derived manifests, not an “allow known extras” exception.
- Source anchoring intentionally cannot certify a foreign tree from a different package revision. An older but internally intact universal install may remain `malformed` when checked by a newer package whose manifest bytes differ. Accepting historical manifests would require a packaged digest history or a stronger version/trust design; silently trusting the installed older manifest would violate the stated source-anchor constraint.
- The filename and schema say “add-on” even for the core. Reusing them is the smallest compatible change; renaming the schema would add migration complexity without improving defect detection.
- The generator's current no-argument behavior checks only directories that already opted in. That behavior must change, or a newly added seventh skill can silently repeat this defect.

## Risks

- A stale committed manifest can block a correct local install. Deterministic generation plus mandatory CI, prepack, portable-build, and release inventory checks is therefore part of the fix, not optional release hygiene.
- Treating `valid-unmanaged` as ownership would allow destructive replacement/removal of foreign-managed trees. Keeping the marker-only ownership predicate and extending the existing no-`--force` regressions prevents that semantic leak.
- A core projection verifier that tolerates undeclared extras would weaken exact-manifest semantics and could recreate false greens. Expected layouts must enumerate the complete file set and reject additions, removals, renames, symlinks, and byte changes.
- Hashing all six trees increases doctor/status work, especially for `parley-design-check` and `parley-bidding`, but the payloads are small enough that correctness should win; performance should be measured in the all-target test rather than optimized speculatively.
