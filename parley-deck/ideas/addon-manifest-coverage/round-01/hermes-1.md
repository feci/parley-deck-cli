## Summary

`doctor` reports five of six skills `malformed` when installed by a foreign installer (the universal `skills` CLI that `README.md` recommends first), because `unmanagedButVerified` can only prove a tree intact when the packaged source ships a `parley-addon.json`, and only `parley-bidding` does. The core skill has a second, independent gap: `unit.addon` is null, so the source is null before the manifest is even consulted. I reproduced this verbatim: `exit=1`, `ok: false`, five `malformed` + one `valid-unmanaged`, every malformed unit carrying exactly the "no install marker" problem. The fix is manifest coverage: ship `parley-addon.json` for all five unmanifested units (four add-ons + the core skill), generated by the existing `build-addon-manifest.js` tool, and add a `sourceRoot` field to every unit so `unmanagedButVerified` can anchor the core skill's proof to its packaged source directory without naming any skill inside the verification function. The exit-code policy already accepts `valid-unmanaged` as healthy, so once the five units verify, `doctor` exits 0 with no exit-code change needed.

## Proposed approach

### Q1 — Manifest coverage, not a semantic change or exit-code change

The fix is **manifest coverage**: ship `parley-addon.json` for all six units. No semantic change to `unmanagedButVerified` is needed — its logic is already correct. It returns `true` when the source has a manifest, the source manifest verifies, the installed manifest matches the source manifest, and the installed payload verifies. The only reason it returns `false` for five units today is that those units ship no manifest, so there is nothing to verify against.

Failure modes each alternative leaves open:

- **Manifest coverage (proposed):** Closes both gaps. After implementation, a foreign-installed full set reports six `valid-unmanaged` and `doctor` exits 0. Residual: a foreign-installed core skill that was then augmented with `plugin.json`/`gemini-extension.json` (e.g. an installer install whose marker was later deleted) would report `unexpected: plugin.json` from `verifyPayload`. This is no worse than today — that tree is already `malformed` — but the error message changes from "no install marker" to "unexpected file." I discuss this in Concerns below.

- **Semantic change alone (broaden what "correct" means without manifests):** Would require defining "provably intact" without a file-level manifest. The only available evidence is the required-files list (`SKILL.md` + a handful of known files), which is exactly the check the manifest was introduced to supersede. A tree gutted to `SKILL.md` plus the required files but missing everything else would pass — that is the B3 false green. This option reopens B3 and I reject it.

- **Exit-code change alone:** Would make `doctor` exit 0 on `malformed` units, which is silently downgrading defect reporting. This does not fix the problem; it hides it. I reject it.

- **Combination (manifest coverage + minor exit-code refinement):** The current exit-code logic already treats `valid-unmanaged` as healthy (`doctorCommand` line 381–386: `skill.status === "valid" || skill.status === "valid-unmanaged"`). No exit-code change is needed. If the team prefers an explicit signal that the tree is not tool-managed, the `managed: false` boolean already carries that fact alongside the status string.

### Q2 — Generated at pack time, committed, drift prevented by `--check` in `prepack` and `npm test`

The existing `parley-bidding/parley-addon.json` is a generated, committed artifact. `scripts/build-addon-manifest.js` generates it; `scripts/build-addon-manifest.js --check` verifies it; `prepack` runs `--check` (so `npm pack` / `npm publish` fail on drift); `npm test` runs `--check` (so CI fails on drift). This is the "release-time inventory check" the installer comments reference (line 1951–1953).

The extension: teach `build-addon-manifest.js` to cover the core skill and the four unmanifested add-ons. Today `listAddons()` explicitly excludes `CORE_SKILL_NAME` (line 42). The change:

1. Remove the `entry !== CORE_SKILL_NAME` filter from `listAddons()` (or add a parallel `listCoreSkill()` that returns `["parley-deck"]`).
2. When no explicit names are given, target all skill directories that carry a manifest OR are in a mandatory set (core + all add-ons). This ensures `--check` verifies every shipped manifest.
3. Generate manifests for `parley-deck`, `parley-design`, `parley-design-check`, `parley-tracker`, `parley-worktrees` with the same `computeManifest` call already used for `parley-bidding`.

**Drift prevention:** A stale manifest (payload edited, manifest not regenerated) is caught at three gates:
- `npm test` → `build-addon-manifest.js --check` → `STALE` exit 1.
- `npm pack` / `npm publish` → `prepack` → `--check` → exit 1.
- At runtime, `unmanagedButVerified` calls `verifyPayload(source)` (line 2135). If the source manifest doesn't match the source files, this returns `false` → `malformed`. So even a stale manifest that somehow shipped would not turn a correct installed tree `malformed`: the installed manifest must match the source manifest (`manifestFileHash` comparison, line 2138–2141), and the source manifest must match the source files. A stale source manifest fails the latter check, so no installed tree can verify against it — the tree reports `malformed`, which is the same as today. The failure mode is "stale manifest makes everything malformed" (detected, loud) not "stale manifest makes a wrong tree pass" (silent, the strictly-worse case the constraint names).

**A stale manifest must not be able to turn a correct tree malformed.** The constraint says this is "strictly worse than today's." With the `--check` gates, a stale manifest cannot ship. If it somehow did, `unmanagedButVerified` would return `false` for every unmarked tree (source verification fails), making them `malformed` — the same as today. The installer's own happy path (marker present) never calls `unmanagedButVerified`, so the marker-managed install is unaffected by source manifest staleness. The `manifestProblems` path for managed add-ons compares against the marker's recorded `manifest.aggregate` and `manifest.sha256`, not against the source manifest, so a stale source manifest does not affect managed installs either.

### Q3 — `sourceRoot` on the unit object; the core skill's source is `path.join(packageRoot, CORE_SKILL_DIR)`

Today `unmanagedButVerified` reaches the source through `unit.addon.root` (line 2125). For the core skill, `unit.addon` is `null` (line 1003), so the source is `null` and the function returns `false` immediately.

The correct source anchor for the core skill is `path.join(context.packageRoot, CORE_SKILL_DIR)` — the directory `skills/parley-deck/` in the package. This is where the skill's files live and where a manifest would be placed.

The change generalizes without naming any skill inside `unmanagedButVerified`:

1. In `targetSkillUnits` (line 995), add a `sourceRoot` field to every unit:
   - Core: `sourceRoot: path.join(context.packageRoot, CORE_SKILL_DIR)`
   - Add-on: `sourceRoot: (discovered.get(name) || {}).root || null`

2. In `unmanagedButVerified`, replace `const source = unit.addon ? unit.addon.root : null` with `const source = unit.sourceRoot || null`.

`unmanagedButVerified` no longer references `unit.addon` at all. The naming of `CORE_SKILL_DIR` lives in `targetSkillUnits`, which already uses that constant (line 124, 140). No skill is named inside the verification function.

**Why `skills/parley-deck/` and not the assembled destination shape.** The core skill's installed destination is assembled from two source locations: `skills/parley-deck/` (SKILL.md, agents/, references/) and the repo root (plugin.json, gemini-extension.json). A manifest at `skills/parley-deck/` covers only the first set. This is correct for the foreign-install case: the universal `skills` CLI copies `skills/parley-deck/` as a single skill directory — it does not copy repo-root files. So a foreign-installed core skill has exactly the files the manifest declares. The installer's own install adds `plugin.json` and `gemini-extension.json`, but that tree has a marker, so `unmanagedButVerified` is never called on it. The "proof anchored to the packaged source" constraint is satisfied: the manifest is at and covers the skill's source directory.

### Q4 — `valid-unmanaged` is the right terminal status; `doctor` already exits 0 on it

`valid-unmanaged` is correct: the payload is byte-verified against the manifest, but the tree is not tool-managed (no marker). The `managed: false` boolean carries the provenance fact for automation that requires tool-managed installs.

`doctorCommand` (line 381–386) already treats `valid-unmanaged` as healthy:
```js
ok: results.every((result) =>
  result.skills.every((skill) =>
    (skill.status === "valid" || skill.status === "valid-unmanaged") &&
    (!skill.runtime || skill.runtime.ok)
  )
)
```
Once all six units can verify, a foreign-installed full set reports six `valid-unmanaged` and `ok: true` → exit 0. No exit-code change needed.

The four-path invariant (install, uninstall, status, doctor) holds:
- **doctor / status:** `valid-unmanaged` (unmarked but manifest-verified). Both use the same `skillUnitStatus` code path.
- **install:** `preflightSkillUnit` (line 1135) blocks an unmarked destination unless `--force`. The foreign install is not overwritten without explicit user action. No contradiction: the destination is unowned, and install agrees it is unowned.
- **uninstall:** `installerOwnsDestination` (line 2432) returns `false` for an unmarked directory. Uninstall will not touch it without `--force`. Consistent with doctor's `managed: false`.

One destination is never simultaneously healthy-and-owned by one command and unowned by another.

### Q5 — Regressions

**Regression that proves the fix:** A test that reproduces the prompt's scenario — copy all six skills verbatim with no install marker, run `doctor --target codex --json`, and assert every unit is `valid-unmanaged` with `ok: true` and `exit 0`. This test fails against the current commit (five `malformed`, `ok: false`, `exit 1`) and passes after the fix. The existing test "a faithfully copied tree with no marker at all is valid-unmanaged" (bidding-addon.test.js:411) already proves this for `parley-bidding`; the new test extends it to all six.

**Regression that proves B3 survived:** The existing test "an unmarked tree gutted to SKILL.md is still malformed" (bidding-addon.test.js:469) must still pass. It must be duplicated for the core skill and each newly manifest-carrying add-on: copy only `SKILL.md` to the destination (no manifest, no marker), run `doctor`, assert `malformed`. The gutting is caught because `manifestFileHash(dest)` returns `null` (no manifest in the gutted tree) → `sourceHash !== installedHash` → `false` → `malformed`. If the gutted tree retains the manifest but drops payload files, `verifyPayload(dest)` finds the missing declared files → `false` → `malformed`. Both paths are covered by the existing `unmanagedButVerified` logic, which is unchanged.

**Regression that proves staleness prevention works:** `build-addon-manifest.js --check` must pass for all six manifests. A test that mutates a payload file and runs `--check` must fail with `STALE`. This is the existing pattern; extending it to six manifests is mechanical.

## Concerns / open questions

1. **Core skill manifest scope vs. installer's destination shape.** The manifest at `skills/parley-deck/` covers 6 files (SKILL.md, agents/manifest.yaml, agents/openai.yaml, references/COOPERATION.md, references/WORKED_EXAMPLES.md, references/compatibility.json). The installer's own destination also includes `plugin.json` and `gemini-extension.json` (from `PAYLOAD_ENTRIES`). If an installer-installed core skill has its marker deleted, `unmanagedButVerified` would call `verifyPayload(dest)` and find `plugin.json`/`gemini-extension.json` as `unexpected` → `malformed`. Today that tree is also `malformed` (source is null), so the user-visible outcome is the same, but the error message changes from "no install marker" to "unexpected: plugin.json." This is a tolerable trade-off — the marker was deleted, re-install is the fix — but the team should decide whether to document it or address it by moving `plugin.json`/`gemini-extension.json` into `skills/parley-deck/` (a larger layout change that would also simplify `PAYLOAD_ENTRIES`).

2. **`build-addon-manifest.js` and the core skill.** Today `listAddons()` explicitly excludes `CORE_SKILL_NAME`. The script's `--check` mode with no names targets only add-ons that already carry a manifest (line 89). Extending coverage requires either removing the exclusion or adding the core skill to the default target set. The core skill has no `runtime` requirement, so its manifest would have no `runtime` block — `computeManifest` already handles this (line 84–87: runtime is optional). Should the core manifest be generated with `--runtime-python` like `parley-bidding`, or with no runtime? The core skill is pure markdown with no Python scripts; no runtime is correct.

3. **The `--check` gate coverage.** Currently `prepack` runs `--check`, which only checks add-ons that already have manifests. After extending coverage, `--check` must verify all six manifests. If a new add-on is added in the future and no manifest is generated for it, `--check` should fail. This requires `listAddons()` (or its successor) to treat manifest presence as mandatory for all shipped skills, not optional.

4. **Gemini and Antigravity targets.** The core skill's installed shape differs for `gemini` (rewritten `gemini-extension.json`, flat `SKILL.md`) and `antigravity` (includes `skills/SKILL.md`). A foreign-installed core skill on these targets would have a different file set than the manifest covers. However, foreign installers (the universal `skills` CLI) target standard skill directories, not Gemini extension or Antigravity plugin paths. The manifest at `skills/parley-deck/` covers the standard destination shape. Should the proposal also handle non-standard target shapes, or is that out of scope?

5. **`manifestProblems` for the core skill.** Today `validateInstalledPayload` calls `manifestProblems` only for `kind === "addon"` (line 2237). For the core skill (kind is `target.kind`, e.g. `"codex"`), `manifestProblems` is never called, so the marker's `manifest` field is never checked for the core. With a manifest shipped, should the core skill's managed path also verify the payload against the manifest? Today the core relies on the required-files list only. Adding manifest verification for the core's managed path would strengthen it but would also encounter the `plugin.json`/`gemini-extension.json` "unexpected" issue on every managed install. I recommend leaving the managed core path on required-files only and using the manifest solely for the unmanaged path — but this means the core's managed path is weaker than the add-ons' managed path. The team should decide whether that asymmetry is acceptable.

## Risks

1. **Stale manifest on the core skill.** The core skill's files change more frequently than `parley-bidding`'s (COOPERATION.md is a living document). A contributor who edits `references/COOPERATION.md` and forgets to run `node scripts/build-addon-manifest.js` would ship a stale manifest. The `--check` in `prepack` and `npm test` catches this, but only if CI runs `npm test` — a contributor who skips tests and publishes via a non-npm channel could bypass `prepack`. Mitigation: the `--check` gate is already in `npm test`, and the existing release discipline (version bump + five channels) is assumed.

2. **False "unexpected" on installer-installed + marker-deleted core skill.** As described in Concern 1. The tree is already `malformed` today; the error message changes. Low risk but potentially confusing for a user who deleted the marker and sees "unexpected: plugin.json" instead of "no install marker."

3. **Manifest coverage creates a new maintenance burden.** Six manifests must be regenerated on every payload edit. The `--check` gate makes this a build failure rather than a silent drift, but it is one more step in the contributor workflow. The existing `parley-bidding` manifest already imposes this; extending to six multiplies the surface.

4. **The `sourceRoot` field changes the unit object shape.** `targetSkillUnits` returns units consumed by `skillUnitStatus`, `preflightSkillUnit`, `stageSkillUnit`, `commitStagedUnit`, and `writeMarker`. Adding a field is additive and should not break consumers that destructure known fields, but any consumer that does `Object.keys` or deep equality on units would see a change. I checked the test suite — tests compare specific fields, not whole unit objects — so this is low risk.

5. **`build-addon-manifest.js` modification touches a release tool.** The script runs in `prepack` and `npm test`. A bug in the modification could break the release pipeline. Mitigation: the change is small (remove one filter, extend the default target set), and the existing `--check` logic is reused unchanged.
