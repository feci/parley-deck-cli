## Summary

The reported symptom has two independent causes, and I measured a third fact that rules out
the obvious fix as stated.

1. Four of the five add-ons ship no `parley-addon.json`, so `unmanagedButVerified` has nothing
   to verify against.
2. The core `parley-deck` unit is not an add-on, so `unit.addon` is null and the function
   returns false before a manifest is consulted at all.
3. **The core skill's installed tree is not a copy of its source tree.** Measured: the source
   `skills/parley-deck/` holds 6 files; an installed core holds 11. The installer pulls
   `LICENSE`, `README.md`, `plugin.json` and `gemini-extension.json` from the *repository root*
   into the destination (`lib/installer.js` lines 143-148). Worse, on the `gemini` target
   `rewriteStagedGeminiManifest` **rewrites** `gemini-extension.json` at stage time:

   ```
   packaged:  "contextFileName": "skills/parley-deck/SKILL.md"
   installed: "contextFileName": "SKILL.md"
   ```

   So one installed core file has destination-dependent bytes that are not knowable from the
   package. "Generate a manifest for each `skills/*` directory" cannot cover the core unit, and
   a naive attempt would make every correct core install report four `unexpected:` entries plus
   one `modified:` on gemini — turning today's false negative into a false positive on the
   installer's own happy path.

## Proposed approach

**Manifest coverage for all six units, with the manifest describing the INSTALLED composition
rather than the source directory.**

- Introduce a single generic notion of a unit's *packaged payload set* — the ordered list of
  (source, destination-relative) entries the installer would copy for that unit. The core
  already has one: `CORE_FILES` plus the root extras. Add-ons have the trivial one (the whole
  directory). `unmanagedButVerified` then anchors to that set for every unit instead of
  reaching through `unit.addon.root`, which answers question 3 without naming any skill.
- Declare destination-rewritten entries explicitly. `gemini-extension.json` on the `gemini`
  target is the only one today. Two candidate treatments, and I would put the choice to the
  round rather than assume it:
  - **(a)** mark such entries `volatile` in the manifest — present and required, contents not
    hashed. Cheap, honest, and it says in the file itself why. Cost: one file per core install
    is outside integrity coverage.
  - **(b)** hash the *post-rewrite* form by running the same rewrite the installer runs. Full
    coverage, but the verifier now has to reproduce installer logic, and the two can drift.
  I lean to (a): a manifest that quietly re-implements the installer is a second source of
  truth, which is the failure mode this whole area keeps producing.
- Manifests are **committed artifacts**, regenerated by a script, with a **drift-guard test**
  that recomputes every manifest from the payload and fails the suite on mismatch. Committed
  rather than pack-time-generated so the file is reviewable in a diff and `npm pack` cannot
  produce a tarball whose manifests were never seen. The drift guard turns staleness into a red
  test rather than a red `doctor` on a user's machine — this is the answer to question 2, and
  the repo already uses this shape for the two `COOPERATION.md` copies.

## Concerns / open questions

**The trade-off I most want the others to attack.** Today, if you install `parley-design` with
our own installer and then edit its `SKILL.md`, `doctor` reports `valid` — nothing hashes it.
After this change it reports `modified: SKILL.md`, i.e. `malformed`. That is a real
user-visible tightening for anyone who tweaks an installed skill in place, and it is not what
this idea was opened to do.

Three positions, and I do not think mine is obviously right:

- **Uniform strictness.** Hash everything for every unit on every path. Consistent, and it
  matches what `parley-bidding` already does today. Cost: local edits become `malformed`.
- **Proof-path only.** Consult the manifest only when there is no marker (to *prove* an
  unmarked tree intact) and leave marker-managed installs as tolerant as they are now. Fixes
  the reported bug with the smallest behavioural delta. Cost: `parley-bidding` is stricter than
  the other five for no principled reason, i.e. the asymmetry moves rather than disappears.
- **Uniform strictness plus a distinct status** for "installer-owned, payload edited" so it is
  not word-for-word the same as a gutted tree. Costs a new status string, which the constraints
  discourage.

Other open questions:

- Does `doctor` already exit 0 when every unit is at worst `valid-unmanaged`? My reading of
  `installer.js:2088` says yes — `parley-bidding` proves it in the reproduction, since it is
  the one unit that does not fail. If that reading is right, question 4 needs no code change
  and the fix is entirely about making the other five provable. Someone should check me.
- The four root extras (`LICENSE`, `README.md`, `plugin.json`, `gemini-extension.json`) are
  currently *not* in the core's required-file list for every target
  (`installer.js:2230-2232` differs per target). If the manifest declares them, the manifest
  and the required-file list become two overlapping definitions of the same thing. Should the
  required-file list be derived from the manifest instead of sitting beside it?

## Risks

- **Reintroducing a false green.** Any widening of the unmarked-tree acceptance path must be
  paired with a regression proving a gutted tree still fails. I will not accept a fix here
  without that test failing against `23a9856`.
- **False positives on the happy path**, described above — strictly worse than the bug being
  fixed, because it fires on installs this tool performed itself.
- **Drift between manifest and payload** if the regeneration script is ever forgotten. The
  drift guard is load-bearing, not decorative; it must run in the default suite.
- **Scope creep into the required-file list and status vocabulary.** Both are adjacent and both
  were ratified by earlier rounds. If the answer needs them changed, that should be argued
  explicitly rather than absorbed.
