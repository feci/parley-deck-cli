## Summary

Everything below was reproduced, not asserted from reading. Sandbox: verbatim copies of all
six packaged skills into an isolated `HOME/.codex/skills`, no markers — the foreign-installer
shape the README documents first.

Measured on the real repo (2.1.0):

- `doctor --target codex` exits 1; five of six units `malformed` with exactly the
  no-marker problem from the prompt; only `parley-bidding` is `valid-unmanaged`.
- B3 holds today: `parley-bidding` gutted to `SKILL.md` (manifest deleted along) is still
  `malformed`, exit 1.

Measured on a **sandbox copy** of the repo with `parley-addon.json` generated into all six
skill dirs (the real repo was not touched):

- The four add-ons flip to `valid-unmanaged` with **zero code changes**.
  `unmanagedButVerified` (lib/installer.js:2124) is already generic; it only ever lacked
  manifests to verify against.
- The core stays `malformed` for exactly one reason: the anchor
  `unit.addon ? unit.addon.root : null` is null for the core. The three proof primitives all
  pass on the verbatim foreign core once a source root exists: `verifyPayload(source).ok`,
  `manifestFileHash(source) === manifestFileHash(dest)`, `verifyPayload(dest).ok` — all true.
- With a two-site patch (core unit gains `sourceRoot`, the predicate reads it): foreign
  full-fleet `doctor` exits **0**, all six `valid-unmanaged`, `managed: false`.
- Under the same patch, every B3 variant still fails closed: foreign core gutted to
  `SKILL.md` (manifest kept *or* deleted), a newly-manifested add-on gutted likewise, and a
  native core with its marker deleted — all `malformed`, exit 1.
- Native install from the manifested source: all six `valid`, `managed: true`, exit 0. The
  native core tree does **not** carry the manifest (PAYLOAD_ENTRIES is unchanged), so the
  marker path is undisturbed.
- Ownership stays fail-closed: `install`/`uninstall` without `--force` report `blocked` for
  every `valid-unmanaged` unit including the core; no marker is synthesized.

So the answer to the idea is: **manifest coverage plus a generalized source anchor. No
semantic change, no exit-code change.** The classification vocabulary and the `doctor` gate
already do the right thing once evidence exists.

## Proposed approach

**Q1 — coverage, semantics, exit code, or combination?**

Coverage + anchor, nothing else.

- *Manifest coverage (recommended).* Ships `parley-addon.json` for the four remaining add-ons
  and the core. Failure modes left open, stated honestly:
  - **Version skew.** `doctor` from installer vX against a faithfully foreign-installed tree
    of repo vY (X ≠ Y) reads `malformed`, because proof is anchored to the running package's
    own bytes. That is the cost of the round-4 ruling that closed the laundered-tree hole;
    the alternative (trusting the installed manifest) re-opens it. Accepted.
  - **Pruning foreign installers.** A foreign installer that strips `*.json` or otherwise
    prunes the payload still reads `malformed`. Correct-but-noisy: absence of evidence must
    not be promoted to health. Accepted.
  - **Native core stays marker-anchored** (see Q3). A native core with a deleted marker stays
    `malformed` — measured; that is the documented B3 posture, not a regression.
- *Semantic change (rejected).* Classifying an unmarked tree as healthy on required-files
  alone re-opens B3 precisely: for add-ons the required-file list is `["SKILL.md"]`
  (lib/installer.js:2228), so a gutted tree would report healthy. This is the exact false
  green the marker requirement exists to close.
- *Exit-code policy change (rejected).* Tolerating `malformed` in the `doctor` gate makes the
  one command users run to check an install green on genuinely broken trees. It treats the
  symptom and destroys the signal.

**Q2 — committed or generated-at-pack, and what stops drift?**

**Committed artifacts, generated by tooling, enforced by `--check`.** The machinery already
exists and is already wired: `scripts/build-addon-manifest.js` regenerates deterministically,
and `package.json` runs `--check` in both `npm test` and `prepack` — I confirmed a one-line
payload edit without regeneration fails `--check` with `STALE`, exit 1. So drift is prevented
(a stale manifest cannot pass CI or reach a tarball) and detected (the check names the skill).

Committed is mandatory, not merely preferable: the universal `skills` CLI installs from the
**git repository**, not the npm tarball. A pack-time-only artifact would not exist on the
README-first install path this idea is fixing, and those installs would stay `malformed`.

Changes needed in the generator: drop the `entry !== CORE_SKILL_NAME` exclusion so the core
is covered; the one-time initial generation names each of the six skills explicitly (the
script's no-names default then refreshes all six, since all carry manifests). No `runtime`
blocks for the five: the core and four add-ons declare no Python floor, and the B6 probe
vocabulary is Python-only today, so `runtimeAvailability` keeps returning `null` for them.

**Q3 — the core's source anchor, generalized.**

The anchor is `path.join(context.packageRoot, CORE_SKILL_DIR)` — the packaged core skill
directory, a constant that already exists (lib/installer.js:124). Carry it on the unit as
`sourceRoot` (add-ons keep `unit.addon.root`), and let `unmanagedButVerified` read
`unit.addon ? unit.addon.root : unit.sourceRoot || null`. The rule becomes "every unit has a
packaged source root; if that source ships a manifest, an unmarked installed tree can be
proven intact against it" — no skill is named in the logic. The no-context fallback in
`targetStatus` (lib/installer.js:1987) simply gets no `sourceRoot` and behaves as today.

One measured subtlety that shapes the design: the manifest describes the **verbatim skill
directory**. The native core is *assembled* — PAYLOAD_ENTRIES adds `plugin.json`,
`gemini-extension.json`, `README.md`, `LICENSE` from the package root, antigravity adds
`skills/SKILL.md`, and gemini rewrites `gemini-extension.json` at staging time. Verified in
the sandbox: the native core tree carries no `parley-addon.json`, and it must stay that way —
do **not** add the manifest to PAYLOAD_ENTRIES, or the native tree becomes a superset its own
manifest flags as `unexpected`. Consequence: the core has two integrity regimes — marker +
required-files for the native shape, manifest proof for the foreign verbatim shape. The
existing test "the core unit never becomes valid-unmanaged" (test/bidding-addon.test.js:796)
keeps passing unchanged, because a marker-deleted *native* core has no manifest in-tree and
correctly cannot be proven. The alternative — per-kind assembled-shape manifests including an
install-time-rewritten gemini manifest — is complexity with no consumer; not recommended.

**Q4 — terminal status and exit policy.**

`valid-unmanaged` is the right terminal status and `doctor` should exit 0 when every unit is
at worst that. **This is already the ratified behavior** (lib/installer.js:381-387) and I
verified it end-to-end: the patched foreign fleet reports all six `valid-unmanaged`,
`managed: false`, exit 0. The distinct status (not `valid`) keeps automation able to insist
on tool-managed installs, and ownership stays fail-closed — measured: `install` and
`uninstall` without `--force` are `blocked` on the `valid-unmanaged` core, `--force`
reclaims. No change needed here; the bug was never the gate, it was the missing evidence.

**Q5 — regressions.**

Fix-proving (fail against the current commit, pass after):

1. *Foreign full-fleet*: verbatim-copy all six skills, no markers → all six
   `valid-unmanaged`, `doctor` result `ok: true`. This is the 00-prompt repro encoded as a
   test; today it exits 1 with five `malformed`.
2. *Core anchor*: an unmarked verbatim core copy is `valid-unmanaged` — the mirror of the
   existing bidding test "a faithfully copied tree with no marker at all is valid-unmanaged"
   (test/bidding-addon.test.js:411). Today: `malformed`.

B3-survival (must pass before **and** after; all measured in the patched sandbox):

3. Existing and untouched: "a tree gutted to SKILL.md is malformed" (:195), "an unmarked
   tree gutted to SKILL.md is still malformed" (:469), the doctor-not-ok gutted test (:558),
   the laundered-tree test (:807), and the native-core test (:796).
4. New: an unmarked **foreign core** gutted to `SKILL.md` is `malformed` — twice: manifest
   deleted (hash compare fails) and manifest kept (payload verify fails on missing files).
   Both arms of `unmanagedButVerified` are exercised.
5. New: a newly-manifested add-on (e.g. `parley-design`) unmarked and gutted to `SKILL.md`
   with the manifest kept is `malformed`.
6. Drift: `node scripts/build-addon-manifest.js --check` stays in `npm test` and `prepack`;
   a stale manifest fails the build before it can certify the wrong tree.
7. Ownership: extend the :763 pattern to the core — `valid-unmanaged` blocks
   install/uninstall without `--force`, synthesizes no marker, and `--force` reclaims the
   unit as `valid`/`managed`.

Implementation surface (deliberately small): five new committed `parley-addon.json` files;
two sites in `lib/installer.js` (`sourceRoot` on the core unit, one line in the predicate);
the core-exclusion removal in `scripts/build-addon-manifest.js`; the new tests above; README
lines 79–81 ("the one skill that ships a parley-addon.json") rewritten; the CHANGELOG known
limit resolved; then version bump plus all five channels per release discipline.

## Concerns / open questions

- **Version skew is the sharpest residual.** A user who foreign-installs at v2.2 and runs
  `doctor` from a v2.1 binary gets `malformed` on a perfectly faithful tree. I accept it
  (the alternative re-opens the laundered hole), but the `malformed` problem text could name
  the possibility ("payload does not match the manifest this installer ships — the installed
  copy may belong to a different version") without changing the verdict. Worth a round-2
  look; wording only, not semantics.
- **`parley-worktrees` has one payload file; `parley-design` has four.** A manifest over one
  file is nearly free but also nearly vacuous — it still catches truncation and stray files,
  so ship it for uniformity rather than exempting small skills by name.
- **The two-regime core** (marker-anchored native, manifest-anchored foreign) is a deliberate
  asymmetry. If a future idea wants the native core byte-verified too, that is an assembled-
  shape manifest or per-kind supplemental file sets — out of scope here, and I would resist
  it: the marker already binds what the installer wrote.
- **Gemini/antigravity foreign shapes.** The universal skills CLI copies skill dirs verbatim,
  so the foreign core it produces matches the dir manifest. Other foreign paths (a hand-run
  `gemini extensions install`) produce different shapes; those stay marker-or-malformed as
  today. No claim made about them.

## Risks

- **Stale-manifest false-malformed on our own happy path** (the constraint's central worry).
  Mitigated, measured: `--check` runs in `npm test` and `prepack`; a byte of payload drift
  fails the build. Residual: a release cut by hand outside `npm pack` could bypass it — that
  is release-discipline territory, not something this idea can close in code.
- **Scope creep into the status vocabulary.** The non-goals exclude reworking
  `valid-unmanaged`/`valid-unselected`. My proposal changes no status, no gate, no exit code —
  it only supplies evidence to machinery that already exists. Any round-2 push to also
  "simplify" the classification should be refused here.
- **Manifest planted into PAYLOAD_ENTRIES by a well-meaning implementer.** That would make
  the native core self-contradictory (superset vs. dir manifest). Regression guard: a test
  asserting the native-installed core does *not* carry `parley-addon.json`, beside the :796
  invariant that keeps it `malformed` when unmarked.
- **Evidence asymmetry across versions of this package.** Older `doctor` binaries will keep
  calling these foreign installs `malformed` regardless of what we ship; the fix only helps
  from the releasing version forward. Stated so nobody expects retroactive repair.
