## What the two rounds established

The idea was opened for a false **red**: `doctor` exits 1 and calls five of six skills
`malformed` after a foreign installer copies them. Both rounds confirmed that, and then found
that the more serious defect runs the other way.

Every claim below was reproduced by at least two participants independently. Where only one
measured something, it is attributed.

### The false red (the reported bug)

Foreign install — verbatim payload, no marker — on released 2.1.0 (`23a9856`):
`doctor` exit 1, `parley-bidding` `valid-unmanaged`, the other five `malformed`, each carrying
exactly `no parley-deck-skill install marker`. Two independent causes: four add-ons ship no
`parley-addon.json`, and the core is not an add-on so `unmanagedButVerified` returns false
before any manifest is consulted (`unit.addon` is null).

Generating manifests into all six skill directories flips the four add-ons to
`valid-unmanaged` with **no code change**, and leaves the core `malformed`. Measured by
claude-1, codex-1, hermes-1 and kimi-1 separately.

### The false green (found during review, more serious)

Raised by codex-1, reproduced independently by claude-1, hermes-1 and kimi-1. On released
2.1.0, with **our own installer** and the marker retained, the four unmanifested add-ons gutted
to a single `SKILL.md` report `valid`, `managed: true`, and `doctor` exits **0**. Cause:
`validateInstalledPayload` requires exactly `["SKILL.md"]` for `kind === "addon"`, and
`manifestProblems` is consulted only when the source ships a manifest.

Shipping the four manifests closes this **with no further code change** — `sourceHasManifest`
becomes true and the existing `manifestProblems` path starts firing. Measured by claude-1,
hermes-1 and kimi-1.

Two further false greens were found that the manifests do **not** close:

- **Legacy markers.** Raised by codex-1, reproduced by claude-1. An install performed by 2.1.0
  records `manifest: false`. After the fix ships, that pre-existing install still reports
  `valid` and exit 0 when gutted, because `manifestProblems` returns `[]` for
  `declared === false` with no manifest present. The fix would reach only users who re-run
  `install` — which nobody does while `doctor` is green.
- **The core's incomplete required-file list.** Raised by hermes-1, reproduced by claude-1. On
  released 2.1.0 a natively installed core survives deletion of `plugin.json`,
  `agents/openai.yaml` and `references/WORKED_EXAMPLES.md` with `doctor` exit 0, `valid`,
  `managed: true` and **zero problems**. The per-target required-file lists enumerate fewer
  files than `PAYLOAD_ENTRIES` actually installs. Independent of foreign installers and of this
  idea's original scope.

### What was ruled out

codex-1's round-1 proposal for per-target "exact expected layout" manifests for the core was
withdrawn by its author in round 2 and is not adopted. kimi-1 measured, and claude-1 and
hermes-1 confirmed, that the installed native core tree does **not** carry a manifest — the
core copy plan does not include `parley-addon.json` — so the packaged core manifest is
consulted only as source-side proof on the unmanaged path, where the tree is a verbatim copy
and the divergence never arises.

claude-1's round-1 objection (that the core's four root extras and the per-destination
`gemini-extension.json` rewrite make a core manifest unworkable) was withdrawn by its author in
round 2 for the same reason: the measurements were right, the conclusion did not survive
checking whether the installed core carries a manifest at all.

hermes-1 corrected its own round-1 claim that the anchor change is a two-site edit; it measured
four sites, including an on-disk-not-selected branch that the two-site version misses.

## Agreed fixes

1. **Ship `parley-addon.json` for all six units** — `parley-deck`, `parley-design`,
   `parley-design-check`, `parley-tracker`, `parley-worktrees` join `parley-bidding`.
   Generated by `scripts/build-addon-manifest.js`, committed, `--check` wired into `npm test`
   and `prepack`. No `runtime` block for the five (none declares an interpreter floor).

2. **Make manifest coverage mandatory, not opt-in.** Drop the `CORE_SKILL_NAME` exclusion from
   `listAddons()` and change the no-argument default so `--check` enumerates every
   `skills/*/SKILL.md` directory. A skill without a manifest is a `--check` failure. Without
   this, a seventh skill repeats the defect silently. Raised independently by codex-1 and
   hermes-1 in round 1.

3. **Give every unit a `sourceRoot` and have `unmanagedButVerified` read it** instead of
   reaching through `unit.addon`. hermes-1 measured that this is four sites, not two — the core
   unit, the add-on expected loop, the on-disk-not-selected loop, and the no-context fallback
   (which stays without a `sourceRoot` and behaves as today). The predicate names no skill.

4. **Close the legacy-marker hole.** In `manifestProblems`, `declared === false` combined with
   `sourceHasManifest` must report that the marker predates this skill's manifest and the
   install should be re-run. This mirrors the already-ratified precedent one branch above it at
   `installer.js:2280`, which does exactly this for the schema-undefined case. Accepted
   knowingly: upgraded users with a pre-fix install will see a red `doctor` until they re-run
   `install`, and the CHANGELOG must say so and say how to repair it.

5. **Close the core's incomplete required-file list** by deriving it from the copy plan
   (`PAYLOAD_ENTRIES` plus target-specific entries, with the optional entries staying
   optional) rather than maintaining four hand-written per-target lists. hermes-1's
   counter-proposal, endorsed by kimi-1 as "data, not machinery". This catches deletion, not
   modification — the same limit the current list has.

6. **Regressions**, each of which must fail at `23a9856`:
   - foreign verbatim copy of all six → six `valid-unmanaged`, `doctor` exit 0;
   - the same copy with each unit gutted to `SKILL.md`, manifest kept and manifest deleted →
     `malformed`, exit 1 (B3, unmarked);
   - native install with markers retained, each add-on gutted to `SKILL.md` → `malformed`,
     exit 1 (this is the false green; it currently passes as `valid`);
   - a genuine `markerSchema: 2, manifest: false` fixture → flagged re-install-to-validate,
     and repaired by re-running install;
   - native core minus a file that the current required-list omits → `malformed`;
   - source drift: edit a payload without regenerating → `--check` fails and install preflight
     writes nothing;
   - ownership unchanged: a `valid-unmanaged` fleet blocks install and uninstall without
     `--force`, and no marker is synthesized.

7. **Update the documentation in the same commit.** `README.md:79` and the `CHANGELOG.md`
   "Known limits" section both state that `parley-bidding` is the only skill shipping a
   manifest. Both become false.

## Deferred follow-ups

1. **Byte-level integrity for the core's managed path.** After fix 5 the core catches deleted
   files but still not modified ones, because the native core tree carries no manifest and
   nothing hashes it. Closing that needs either an assembled-shape manifest or a whitelist for
   the destination-rewritten `gemini-extension.json`; both were considered and rejected as
   larger than this idea. Recorded rather than hidden.

2. **A foreign-installed tree from a different package revision stays `malformed`.** Source
   anchoring cannot certify a payload whose manifest bytes differ from the installed package's,
   even when that tree is internally intact. Accepting historical manifests would need a
   packaged digest history. Raised by codex-1.

3. **A natively installed core whose marker was deleted reports `malformed` although its bytes
   are correct**, because the native tree carries the four root extras and no manifest and so
   cannot match the packaged source layout. Fail-safe, and strictly better than today where all
   five are false red, but it is the same false-red shape surviving in one corner. Raised by
   claude-1 against kimi-1's round-1 result.

4. **`parley-addon.json` and the `parley-addon/1` schema keep an "add-on" name now that the
   core carries one too.** Reusing them is the smallest compatible change; renaming would add
   migration cost without improving defect detection. Raised by codex-1.

5. **Existing tests that encode the current file counts and `manifest: false` behaviour will
   need updating** — hermes-1 names `design-addons.test.js`'s "exactly the four doctrine files"
   assertion among them. These are expected updates, not regressions, but each must be checked
   individually rather than bulk-edited.

## Amendment 1 — three corrections from kimi-1's signoff, accepted by the drafter

Appended rather than edited into the body above: codex-1 and hermes-1 signed the body as it
stood, and rewriting signed text would invalidate their signoffs. All three corrections are to
claude-1's draft, all three are accepted, and the implementer follows the amended form.

**1.1 — The regression header overclaims (accepted).** "Regressions, each of which must fail at
`23a9856`" is wrong for two of its own bullets. The unmarked gutted-copy bullet and the
ownership bullet **pass at `23a9856` today and must keep passing** — they are survival guards
for invariants this change must not break, not tests that prove the fix. Writing them to fail
at `23a9856` would be an error. The list splits into:

- *fix-proving* (must fail at `23a9856`): the foreign six-unit `valid-unmanaged` fleet; the
  native marker-retained gutted add-ons; the legacy `manifest: false` fixture; the native core
  minus a file the current required-list omits; source drift.
- *survival guards* (must pass before and after): unmarked gutted copies stay `malformed`;
  ownership still blocks install and uninstall without `--force` and synthesizes no marker.

**1.2 — A guard agreed in the rounds is missing from the list (accepted).** Add: the natively
installed core must **not** carry `parley-addon.json`, asserted per target. Pass-before-and-
after. Without it nothing prevents an implementer from adding the manifest to `PAYLOAD_ENTRIES`,
which would make the native core a superset that its own source manifest flags as `unexpected`
— the exact failure mode "What was ruled out" says this design avoids. Raised as a risk guard
by kimi-1 in round 1 and as regression (e) by codex-1 in round 2; the drafter dropped it.

**1.3 — The stated cause of the false green is not the code path (accepted).** The draft says
`manifestProblems` "is consulted only when the source ships a manifest". It is not:
`validateInstalledPayload` (`lib/installer.js:2237`) calls it for **every** add-on with a
marker — `sourceHasManifest` is merely an argument, used in the schema-undefined branch. The
false green comes from the `declared === false` branch (`:2299`) returning `[]` when no manifest
file is present. Verified in the source by claude-1 before accepting. The draft's own
legacy-marker bullet already described this correctly, so the body contradicted itself; this
amendment settles it in favour of the code. No agreed fix changes.
