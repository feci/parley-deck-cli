# Independent trajectory runner/helper integration

## Behavior

`parley trajectory verify --dir DIR --idea ID --verifier ID --yes` selects an
existing non-implementer participant and invokes its configured headless CLI
through RunConsult and the common instrumented runner. The private parent request
freezes the canonical source root, shared ticket, run identity, original named
material commands and the idea quorum before launch. Required request, directory
and parent-directory persistence barriers precede spawning the verifier.

The typed runner context detaches pointer-bearing ticket fields. The actual
launch boundary reserves its instrumented invocation in the shared journal
before spawn. A phase label alone cannot provide authority. Changed root, run,
idea, phase or participant, unobserved handoffs and repeated tickets refuse with
retained terminal telemetry. The binding is separate from replaceable launch
metadata. Existing launch/step/monetary accounting and shared full-context
rendering remain active; the new phase takes the conservative full-context path.

The selected participant is instructed to invoke the exact `trajectory
verify-helper` command once. The helper requires exact request bytes and its
original private path, inherited run/agent/process marker, unchanged material
scope/quorum and the shared ticket. It calls the existing exclusive durable
captured-source execution journal, including actual AB/BA execution and retained
failed/partial observations. Textual PASS cannot substitute for the helper.

The parent compares its observed terminal record with persisted telemetry and
requires the selected process's successful exit, original run/idea/phase/agent,
exact request and current material scope/quorum, complete matching journal
receipt and a helper PID/time within the observed invocation. It derives the
assessment from retained actual executions and records request/terminal/receipt
digests in an exclusive private parent result. Failed startup, provider/process
failure, failure after a successful helper, missing receipt, changed authority or
lost parent-result publication cannot return an accepted assessment. A new CLI
call cannot silently retry the original reserved verification ticket.

## Scope and trust limits

Exit zero means a complete observed comparison, including possible regression
or inconclusive outcomes. `trajectory_pending` remains true. No fixup charge is
reset, no new patch is authorized, no quorum changes and no implementation closes.
Complete charge-derived ordered evaluation, retained review escalation and
explicit operator recovery/continuation remain unfinished. Existing staged-index
or unavailable-history reconstruction refusals remain intact.

This is cooperative runtime attribution. Inherited labels and mutually consistent
same-UID files are not cryptographic model/human identity. The helper must be
invoked by the selected CLI; tests of that path use synthetic executable agents,
not actual model proposals or participant-owned acceptance. The CLI presently
requires POSIX and a configured headless participant; unsupported modes refuse.
A Windows cross-build does not establish Windows execution support.

Parent requests contain original commands and private paths under ignored
`.parley-runtime/trajectory-verification/<run-id>/`. They are not public telemetry.
The shared charge journal remains the source of retained paired observations.
Failed pre-launch preparations and missing terminal receipts stay pending, with
no automatic recovery. Parent-result readback/reconciliation at a future
trajectory-resolution transition still needs to enforce the exact retained
request, terminal and receipt; this checkpoint does not provide that transition.
