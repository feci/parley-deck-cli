## Position changes since round 1

Three of my round-1 positions hardened into disagreement with the convergence, and one moved toward codex-1. I want to name each shift explicitly rather than restate agreement.

1. **On the overlay addressing scheme, I was wrong and claude-1/codex-1 are right.** My round-1 proposal used section-number anchors (`## override §N`). kimi-1 converged on the same idea. But section numbers are positional, not stable: the next meta-protocol-change idea that reorders or renumbers §8 and §10 (already non-sequential today — §10 precedes §9 in the file) silently retargets every `## override §10` entry. claude-1's stable block IDs (`id="pipeline"`) and codex-1's registry of named block IDs both survive a renumber because the identity is the ID, not the position. I withdraw the section-anchor scheme. The core should carry stable IDs.

2. **On codex-1's sandbox claim, I moved toward codex-1 — but only partially.** I re-read the codebase. Parley already ships one real OS-enforced sandbox: the codex adapter launches with `--sandbox workspace-write` (discover.go:202,207) and the codebase's own honesty rule marks only codex as `Scope: "workspace"` (discover.go:89-108, Confined() == true only for codex). So codex-1 is factually correct that real prevention IS possible for Parley-launched codex agents — the child process inherits a seatbelt profile that denies writes outside the workspace. I was too absolute in round 1 when I said "prevention is not achievable." It is achievable for one adapter, today, and the codebase already distinguishes it. What I maintain against codex-1 is the scope: this covers exactly one of six adapters, and it does NOT cover the facilitator itself (Parley Deck CLI), which runs unsandboxed with the user's full privileges.

3. **On per-idea pinning, I moved toward codex-1's content-addressed snapshot.** My round-1 proposal (version+hash reference) is insufficient for the case claude-1 raised: an idea decided under a protocol without §15 must stay interpretable if the core later adds §15. A version+hash pointer into a mutable `~/.parley` re-resolves against whatever bytes are there now. The exact rendered Markdown, stored once per distinct effective hash, is what makes a June idea still readable in December. codex-1's dedup-by-effective-hash keeps the storage cost bounded. I now support storing the snapshot, with the caveat in §4 below.

4. **On the sealed/virtual/extension split, I now think two verbs is right but the *open* set everyone proposed is too large.** claude-1 opened §12 pipeline, §11 transport parameters, timeouts, §4.0 thresholds. kimi-1 opened §0, §6, §8, §11, §13, Appendix A. The evidence is one genuine local override in 36 decks, and it was governance that belongs in the core. Opening 5-6 sections "because constraint 3 requires override to exist" is designing for hypothetical demand — exactly the over-engineering CLAUDE.md §2 warns against. The two-verb mechanism should exist; the *initial open set* should be near-empty.

### @codex-1

You wrote the most rigorous round-1 artifact. Three of your positions are correct and I adopt them: stable block IDs over heading anchors, content-addressed effective snapshots with dedup, and the empty-overlay-forbidden rule (absence is the canonical no-customization state — this directly prevents 36 mechanically generated overlays from becoming the next 36 stale copies).

The sharp disagreement is enforcement. You claim real prevention IS possible for Parley-launched agents via an OS sandbox that children inherit. I checked the codebase. You are **partially right, and I was wrong in round 1 to say prevention is impossible without qualification.**

**What the sandbox covers (codex-1 is right here):** The codex adapter launches with `--sandbox workspace-write` (discover.go:202). The codebase's own honesty rule marks this as the only adapter with `Scope: "workspace"` and `Confined() == true` (discover.go:89-108). A codex agent launched by Parley runs under a seatbelt profile that denies writes outside `{root}`. If `~/.parley` is outside the workspace root — and it is, by definition — the codex agent **cannot** write to it. This is real OS-level prevention, not a speed bump. The child inherits it. So for codex participants in a Parley run, "prevented from editing the global core" is a true statement today, not security theater.

**What remains unprotected (where codex-1 overstates):**

1. **Five of six adapters have no enforced sandbox.** claude (`--add-dir`), hermes (`--yolo`), agy (`--dangerously-skip-permissions`), and the ACP-catalog agents all have `Scope: ""` — the codebase explicitly says these are "a permission grant, not an enforced sandbox" (discover.go:347,379). A claude participant launched by Parley CAN write to `~/.parley`. For these agents, the honest guarantee is detection + attribution, exactly as claude-1/hermes-1/kimi-1 said in round 1. codex-1's "managed prevention" claim is true for one adapter and false for five.

2. **The facilitator itself (Parley Deck CLI) is unsandboxed.** The CLI that launches the agents runs with the user's full privileges. `syncConsumerProtocol` (preflight.go:488) writes to `COOPERATION.md` in the deck. `parley core upgrade` would write to `~/.parley`. The facilitator is the one process that MUST be able to write to the core (for upgrades) and MUST NOT be sandboxed away from it. So the sandbox covers the agents but not the launcher — and the launcher is where an agent-driven attack would actually execute (an agent that convinces the facilitator to run `parley core upgrade --yes` with a crafted candidate). codex-1's "a headless protocol publish operation is unavailable from an agent run" is a CLI design choice, not an OS guarantee — and it is defeated the moment an agent can influence what command the facilitator executes next.

3. **macOS specifics.** codex's `--sandbox workspace-write` uses macOS seatbelt (the fail-classifier matches `seatbelt` errors, failclass.go:38). `sandbox-exec` is the lower-level macOS mechanism but is deprecated and its profiles are fragile. The reliable path is the one codex already uses: the adapter's own `--sandbox` flag, not a Parley-imposed `sandbox-exec` wrapper. Parley should NOT try to impose its own seatbelt profile on agents — that duplicates what the adapter already does and breaks the first time an adapter changes its sandbox semantics. The correct design: Parley reads `Confined()` from the adapter spec (discover.go:105) and reports prevention only for adapters where it is true. For all others, detection only. This is exactly the honesty rule the codebase already encodes.

**Concrete resolution of the disagreement:** codex-1's "managed prevention" is real but adapter-scoped, not universal. The design should state: "For adapters with `Confined() == true` (currently codex only), a Parley-launched agent is prevented from writing the global core by the OS sandbox the child inherits. For all other adapters and for the facilitator itself, the guarantee is detection + attribution + fail-closed blocking — not prevention." This is not a compromise; it is the precise truth, and it is already encoded in the codebase's `Scope`/`Confined` distinction. codex-1's own concern ("if one adapter can invoke an unsandboxed desktop helper, the prevention claim must be downgraded") is the same point — the claim is per-adapter, not global.

## New concerns / questions

1. **The extension point's position matters for rendering idempotency.** If extensions append "after the last core section," and the last core section changes between versions, the extension's position shifts. With stable IDs, the extension point should be a named block ID (e.g. `id="project-extension"`), not "the end of the file." The renderer inserts extension entries at that ID. This makes the render deterministic regardless of core section reordering.

2. **The skill's bundled snapshot and the `~/.parley` core — which is upstream?** Today there are three protocol surfaces (my round-1 concern #3): the embedded default (`internal/protocol/defaults/COOPERATION.md`), the live deck, and the skill's bundled snapshot (`parley-deck-skill/skills/parley-deck/references/COOPERATION.md`). The drift guard (drift_test.go:46) enforces embedded == live (modulo zones). The new model adds a fourth: `~/.parley/COOPERATION.md` (the core). The relationship must be: the skill's bundled snapshot is the *release source*; `parley core init`/`upgrade` copies it to `~/.parley`; the embedded default is the *bootstrap template* (what `parley init` writes before a core exists); the deck's generated copy is the *view*. The drift guard should then compare: embedded == skill-bundled (release integrity), `~/.parley` core == deck-pinned-hash (adoption integrity), and deck-generated == render(core+overlay) (generation integrity). Three checks, not one.

3. **`protocolRole: source` inverts.** Today the source repo's deck is the protocol upstream (preflight.go:389-395 — preflight never auto-writes it). With a global core, the source repo's `~/.parley/COOPERATION.md` IS the core, authored directly by the user, and the deck copy is generated from it. The `source` role should mean "the core is authored here" — the user edits `~/.parley` directly and `parley protocol render` generates the deck copy. This inverts the current flow and needs explicit handling in the implementation. I raised this in round 1; no one addressed it. It is a real implementation gap.

4. **Per-idea snapshot storage: I support codex-1's content-addressed snapshot, but `sessions inspect` should report the pointer, not the content.** codex-1 wants the exact rendered Markdown stored as an immutable artifact. claude-1 and kimi-1 want a version+hash reference. The resolution: store the snapshot (codex-1 is right that a pointer into a mutable store re-resolves), but `sessions inspect` reports the *compact identity* — `core-version: 2.5.1 / core-sha: a1b2c3 / effective-sha: d4e5f6 / snapshot: ideas/<slug>/protocol-snapshot-<effective-sha>.md` — not the full 1344-line content. The snapshot is retrievable on demand (`sessions inspect --protocol`), but the default view is one line. This gives fidelity (the snapshot exists and is immutable) without flooding every inspect output.

5. **opencode-1's absence is noted and not counted.** Per the inbox record, opencode-1 was invoked four times and produced no round-01 artifact. It is silent for this round. I do not treat its absence as agreement, disagreement, or a quorum problem — four participants satisfy §5, and opencode-1 may rejoin by writing its own artifact in a later round. The follow-up question (does opencode need a longer timeout or smaller context before being relied on as a quorum member?) is worth a separate inbox note but is out of scope for this idea.

## Current proposal

The smallest shippable version, ranked by drift-reduction-per-effort:

**Rank 1 — Ship this week: the core store + the renderer + the drift guard, no overlay.**
This is the piece that reduces drift the most for the least mechanism. `parley core init` writes `~/.parley/COOPERATION.md` from the skill's packaged body and records `coreSha256` in `~/.parley/version.json`. `parley protocol render` generates `parley-deck/COOPERATION.md` from the core + the six identity zones (the exact logic `mergePreservingZones` already does, just with the core as the named source instead of "the packaged body"). The drift guard compares deck-generated == render(core) modulo zones. No overlay, no block IDs, no sealed/virtual split yet. This alone eliminates the 36-flat-copy problem for 35 of 36 decks — the same 35 that the 2026-08-06 sync already proved are pure-core + identity zones. The one deck with a real local section keeps its committed copy as-is until Rank 2 ships. Cost: one new command, one reuse of existing merge logic, one new test. Drift reduction: ~97% of the fleet.

**Rank 2 — Ship next: the overlay with stable block IDs, two verbs, near-empty open set.**
The core gains a block registry (stable IDs, sealed by default). The overlay file (`parley-deck/protocol-overlay.md`) supports `replace <id>` and `extend <id="project-extension">`. Initial replaceable blocks: `working-language` (the §6.6 carve-out) and `transport` (§0, already per-deck). One extension point. Every replace entry records the sha of the core block it replaced (kimi-1's stale-override rule). Compatibility check on every core bump: target ID exists, still replaceable, base-block sha matches. Outcome: block + quarantine, never auto-migrate. Cost: block registry, overlay parser, compatibility checker. Drift reduction: handles the 1-in-36 case and any future genuine local content, bounded and reviewable.

**Rank 3 — Ship after: per-idea content-addressed snapshots + run-manifest pinning.**
`runmanifest.Manifest` gains `ProtocolVersion`, `ProtocolSha256`, `ProtocolRevision` (parallel to `RosterSnapshot`/`RosterRevision`, manifest.go:49-58). Phase 0 pins the effective protocol hash and writes the snapshot to `ideas/<slug>/protocol-snapshot-<effective-sha>.md` (deduped by hash). `sessions inspect` reports `stale-protocol` on drift, with the compact identity line (core-version / core-sha / effective-sha / snapshot path). Cost: two manifest fields, one snapshot writer, one inspect field. Drift reduction: makes historical ideas interpretable under the exact protocol that governed them, not whatever the core says now.

**Rank 4 — Ship last: the enforcement stack.**
Read-only file mode (0444, speed bump). Content-hash verification on every preflight (`drifted-core` status, fail-closed). No CLI write path for agents (`parley core upgrade` requires `--yes` + TTY). Per-adapter prevention claim: `Confined() == true` adapters (codex) report "prevented"; all others report "detected." The facilitator itself is detection-only. This is the honest enforcement model — not "agents cannot," but "agents cannot do so silently, and for sandboxed adapters they cannot do so at all."

**Not shipped as part of this idea:** migration of the 36 flat copies. That is a separate attended fleet operation (Rank 5, post-FINAL), following the roster-migration Stage-4 discipline. The tooling from Ranks 1-4 must exist and be tested before migration begins. Migration is where the 2026-08-06 data loss (the destroyed librade-algoTrader section) recurs if done carelessly — it deserves its own idea or a dedicated FINAL.md appendix with per-deck dry-run, diff, confirm, and rollback.
