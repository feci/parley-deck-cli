## Proposed approach

**Position: yes — the protocol should let the owner designate the implementer, as an explicit, validated, fail-closed overlay on the existing default chain.** The mechanism, per required dimension:

1. **Role scope.** The designee executes FINAL — whatever work product FINAL specifies: code, protocol text across the three copies, docs, release evidence gathering. The role binds Phase 5-8 execution only. It never absorbs the drafter role, never reviews or goal-checks its own work (already machine-enforced: `driver_impl.go:415-417` refuses `checker == implementer`; `consensus.go:730-748` drops the implementer from review-round expectations), and never overrides §7/§14 human gates (core publication stays owner-attended; the TTY refusal is untouched).
2. **Two designation levels and precedence.** Per-idea: a `00-prompt.md` frontmatter field (I propose `designated_implementer: <agent-id>` — a name distinct from `IMPLEMENTATION.md`'s `implementer:` *record*, so designation and outcome stay greppably separate; naming is bikesheddable). Global: a `[defaults]` key in `~/.parley/agents.toml` (e.g. `default_implementer = "<agent-id>"`). **The global default ships UNSET — absent key, no agent named, behavior byte-identical to today.** Proposed precedence: per-idea field > uncontested perfected claim > global default > existing tail (FINAL drafter → durable frontmatter → current fallbacks). Rationale: specificity and visibility beat standing config; the per-idea field is an explicit owner/author act frozen at Phase 0 and outranks a participant's unilateral claim; the standing default deliberately yields to a volunteer the owner can see during the claim window. The alternative ordering (global default > claim) is my open question O1 below.
3. **Unavailable designee.** Fail closed, never substitute silently. At kickoff the §9.0 ping validates the designee's availability; an unavailable designee is a preflight gate resolved only by editing the field, owner-confirmed exclusion per §9.0, or removing the designation. Mid-Phase-5 unavailability follows §5 (ping, watchdog, user-confirmed quorum change) and then escalates for re-designation or explicit fallback — mirroring the declared-facilitator deadlock pattern that escalates instead of falling back (`driver_impl.go:61-63`, CHANGELOG 1.49.0 wording in V9).
4. **Drafter separation and self-contained FINAL.** Drafter and implementer stay distinct roles; designation must not auto-confer drafting. Because designation makes drafter ≠ implementer the *common* case, FINAL's self-containment rule (`COOPERATION.md:433`, today phrased for complex/auto_implement/driver/pipeline ideas) becomes load-bearing for every designated run: the driver should validate FINAL's required sections and observable acceptance criteria before Phase-5 dispatch and fail closed on gaps, rather than discover them through the implementer.
5. **Reviewer diversity.** Designation shrinks the reviewer set to "all participants except the designee" (with this roster: 2 reviewers on deliberation). Existing gates carry the load and stay unchanged: LE-3 warning plus `require_model_diversity: true` escalation when every reviewer shares the implementer's model (`driver_impl.go:179-211`), the invokable-non-implementer-reviewer floor (V5), and the auto-close requirement of ≥2 independent reviewers (LE-11, `COOPERATION.md:684-687`). Add only a validation warning when the designee's model equals a reviewer's, and a hard gate if designation would leave zero invokable non-implementer reviewers. A *persistent* global default raises a systemic habituation risk (same model always implements, same two always review) — that is evidence the post-release recommendation report must carry, not a reason to block the mechanism.
6. **Claim fallback stays.** With both designation levels unset, behavior is exactly today's: claim window, then FINAL-drafter default. The claim mechanism is retained, documented as the participant-initiated override, and — new — the driver should honor a perfected claim by resolving it into the same durable channel (see 7), closing A1 rather than leaving the claim machine-invisible.
7. **Driver and preflight support, fail-closed.** (a) Unify the two `resolveImplementer` copies into one function (natural home: `internal/protocol`, beside `facilitator.go`) with an explicit empty-case policy parameter, so the driver's launch selection and the consensus review-round expectation cannot diverge again (V8, A5). (b) Resolution order gains the designation sources first: per-idea field → perfected claim → global default → `IMPLEMENTATION.md`/`FINAL.md` frontmatter → existing fallbacks. (c) Absent designation = default chain; **present-but-invalid designation = hard stop, never silent fallback** (unknown id, non-participant, declared facilitator without `facilitator_participates: true`, or zero remaining reviewers). (d) New preflight gate kind beside `facilitatorConflictGates` (A4) covering those conflicts plus a global-default roster-membership check — implemented and tested now even though the global ships UNSET. (e) `parley trajectory configure --implementer` must agree with the resolved designee; mismatch is a gate, not a warning (A3). (f) The implementer launch records the designation *source* (per-idea / claim / global / drafter-default) in the run event log for audit.
8. **Design-round and signoff participation.** The designee remains a full participant: writes round files, signs `consensus.md`, signs review consensus (Phase 7 already includes the implementer). Designation is an execution assignment, not a facilitator-style exclusion — a FINAL that binds an executor who never signed its feasibility is exactly the failure mode signoffs exist to prevent. The designee still never authors a Phase-6 review of its own work.
9. **Resolver consistency.** Covered by 7(a): one resolver, two call sites, documented empty-case policy (driver: bounded fallback; consensus: fail-closed full list — the current deliberate difference becomes an explicit parameter instead of accidental drift surface).
10. **Owner-decision boundary.** The release ships the mechanism with the global default UNSET and does not name any agent as the owner's default implementer. Post-release, participants file a recommendation report with evidence — per-implementer review-finding statistics (e.g. V11's 1 CRITICAL + 8 MAJOR caught by a non-implementer reviewer), availability history, token cost, and model-diversity effects — for the owner to decide. I deliberately name no default in this artifact.

## Risks

- **Role ossification.** A settable default can harden into a permanent implementer-by-convention, eroding model diversity of *execution* evidence. Mitigation: UNSET at ship, post-release evidence report, owner decision — plus periodic retro review via §13.
- **Habituated reviewer pair.** A fixed implementer means a fixed reviewer set; rubber-stamp risk concentrates even with model diversity. LE-3 mitigates cross-model sameness, not reviewer habituation; the post-release report should measure findings-per-review by implementer.
- **Resolver re-drift.** A third input source doubles the drift surface the MIN-7/F15 history already exposed (A5). Unifying the resolvers is part of the mechanism, not optional cleanup.
- **FINAL self-containment failures surface late.** With drafter ≠ implementer common, under-specified FINALs hit the designee at Phase-5 start. The pre-dispatch FINAL validation (dimension 4) converts this from a mid-run stall into a kickoff-visible gate.
- **Validation gaps in dormant paths.** The global-default path ships UNSET and will see no live traffic until the owner sets it; its validation must be covered by tests now, or the first real use is the first test.
- **Scope creep into release.** This idea's mechanism is deliberation-track protocol work; the release ordering (prior release completion, version selection, all-channel verification) belongs to the organizer's release step per the brief, and no participant publishes or merges before it.
