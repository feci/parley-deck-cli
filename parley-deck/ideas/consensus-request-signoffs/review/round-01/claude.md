## Findings

- `MAJOR` internal/app/consensus_request_signoffs.go:287 — `validateRequestedSignoff` only iterates `beforeByAgent` when checking foreign blocks, so it catches modifications/removals of pre-existing signoffs but never enforces "exactly one new canonical signoff" (FINAL.md scope and `Implementation details` bullet "verify exactly one new canonical signoff exists for the expected participant"). A buggy or rogue invoked agent that appends two valid blocks — its own plus a forged one for a participant not yet signed — passes validation. If that forged participant is later in the same request batch, the next iteration's `beforeByAgent[agentID]` check (line 280) does fire, but if the forged participant is not scheduled in this run the rogue signoff persists silently and even moves consensus to `ready`. Fix: also iterate `afterByAgent` and reject any agent ∈ after but ∉ before whose ID is not the invoked one.
- `MINOR` internal/app/consensus_request_signoffs.go:118-146 — On a mid-loop failure (validation error or non-zero-after-append), the function returns the wrapped error without printing the accumulated `successes` list. FINAL.md `Failure behavior` explicitly requires "print which signoffs succeeded before failure". Per-agent `Accepted signoff from X` lines are emitted as the loop progresses, but a consolidated summary is missing. Fix: print `successes` (or "Signoffs accepted before failure: ...") to stdout/stderr before returning the error.
- `MINOR` internal/app/consensus_request_signoffs.go:343-349 — The "Canonical block shape" embedded in the prompt template shows only `Status:` and `Notes:` and omits the `Counter-proposal (required if ❌): ...` line. The prose above does instruct the agent to include a counter-proposal for BLOCK, but agents that copy the literal canonical shape will produce a malformed BLOCK block; the validator then rejects it via `after.Errors`. This isn't a correctness bug, but it raises the agent failure rate for the BLOCK path the tests cover. Fix: extend the canonical shape with the `Counter-proposal (required if ❌):` line shown when status is BLOCK, matching `consensus.signoffBlock`.
- `MINOR` internal/app/consensus_request_signoffs.go:202-208 — Missing/unconfigured runner errors (`participant X has no configured runner entry`, `participant X runner is not installed`) propagate as plain errors and the top-level wrapper maps them to exit code 1 (line 49-52 only treats `errRequestUsage` / `errRequestNeedsConfirmation` as code 2). FINAL.md's preflight section frames these as safety/preflight failures alongside other preflight rejections that do exit 2 (unknown participant, already signed, hosted-without-yes). The implementer flagged exit-code semantics for review explicitly. Either wrap with `errRequestUsage` so all preflight rejections share an exit code, or document the runtime/usage split explicitly.
- `NIT` internal/app/consensus_request_signoffs.go:324 — Prompt uses `%q` for `agentID` in two places, rendering as `participant "alpha"` (with Go-quoted escapes if the ID ever contains special chars). Existing internal participant IDs are plain identifiers, so the practical effect is just stylistic noise, but `%s` would read more naturally and match how the canonical block is rendered a few lines below.
- `NIT` internal/app/consensus_request_signoffs.go:239-263 — `runSignoffAgent` re-implements timeout wrapping using `agent.TimeoutMS` directly rather than going through `runner.timeoutForAgent` / the runner package's existing helpers. Behaviour matches today, but it's a second source of truth for the default-timeout semantics; consider exposing the runner helper.

## Open questions

- Should the prompt explicitly forbid edits to non-signoff sections of `consensus.md` (e.g. the `## Agreed decisions` body) and the post-invocation validator detect such edits, or is the intent to scope ownership only to signoff blocks as the current implementation does? The prompt currently says "Do not edit or rewrite any existing line", but the validator only inspects parsed signoffs.
- Is the deferral of durable per-agent run logs (IMPLEMENTATION.md "Deviations") acceptable for this slice, or should at least the child's stdout/stderr be tee'd into the run-state directory so failures are inspectable later? Today the parent's terminal is the only record.
- Should the hosted-gate confirmation also be required when a hosted backend is selected only because the user passed `--participants` containing a single hosted agent? Currently it is (any selected hosted ⇒ requires `--yes`), which matches FINAL.md; flagging only to confirm the intent.

## Summary

Implementation matches the FINAL.md scope cleanly: command wiring, dry-run output, participant/runner preflight, hosted gate, and the happy/BLOCK/non-zero-after-append paths are all covered by focused tests using fake CLIs. The principal correctness gap is the missing "exactly one new signoff" check in `validateRequestedSignoff`, which lets an invoked agent silently forge a signoff for an unsigned, non-batched participant; this should be tightened before relying on the command for unattended runs. The smaller items (success summary on failure, BLOCK template line, preflight exit-code consistency, prompt quoting) are polish that would make the agent-side contract and CLI ergonomics line up with the FINAL.md text. Residual risk areas not covered by tests: forged-foreign-signoff (the bug above), edits to non-signoff sections, and crash/timeout mid-append leaving the file truncated.
