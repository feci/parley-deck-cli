## Proposed approach

**Stage 0 — contract.** "Windows-green" means: unfiltered `go test ./... -count=1` green on hosted windows-latest x64 (longpaths enabled), macOS and ubuntu still green on the same commit, zero new skips/filters/`continue-on-error`, and every genuinely inapplicable test exclusion individually listed with a reviewed reason. Local pre-push smoke for every cycle: `go test ./...` (darwin regression, protects the load-bearing U1/U2 Linux/macOS repairs) + `GOOS=windows go build ./...` + `GOOS=windows go vet ./...` (the vet gate provably catches the test-compile class — Mkfifo matched byte-for-byte).

**Stage 1 — product P1: Windows privacy verification (biggest family, 71 failures).**
Platform-split the two guards at `snapshot.go:162` (directory) and `:544` (file):

- New shared helper, e.g. `fsutil.VerifyPrivatePath(info os.FileInfo, path string, wantDir bool) error`, with two build-tagged implementations.
- `!windows` implementation: exactly today's semantics (`Perm()&0077`, symlink, type checks) — byte-identical behavior, no refactor of the Unix judgment.
- `windows` implementation: read owner + DACL via `GetNamedSecurityInfo`/`GetSecurityInfo` (x/sys/windows, already a direct dependency); the store is private iff every access-granted ACE trustee is within an allowed set {current user, SYSTEM, Administrators}; refuse when any other trustee (Users, Everyone, Authenticated Users, …) is granted, when the descriptor cannot be read, or on volumes without ACL support (FAT/exFAT) — unreadable ⇒ refuse, never weaker. Inheritance from the profile/temp defaults (owner+SYSTEM+Administrators) must be handled by evaluating effective granted SIDs, not by trusting the protected-DACL flag alone.
- Refusal strings: keep the current sentence stable for the common prefix, append the Windows-specific reason (e.g. `snapshot store must be a private real directory: Windows ACL grants access to BUILTIN\Users`), so users see a real, actionable diagnosis instead of a synthesized-mode lie.

**Stage 2 — product P2: gate filenames (10 failures).**
`GatePath` (`gate.go:104`): on Windows only, deterministically percent-encode filename characters invalid on NTFS (`< > : " / \ | ? *` and `%` itself, keeping the mapping injective) in the **filename component only**. `EdgeID` (`gate.go:40`) and the `Edge` field inside the JSON stay verbatim — on-disk identity remains cosmetic, JSON remains authoritative; `LoadGate` and the `parley pipeline` CLI go through the same `GatePath`, so writers and readers agree. Persisted-name compatibility decision (required by the prompt): Unix names stay byte-identical (`>` is legal there and existing decks already carry raw names — zero migration, zero divergence for supported platforms), while Windows has **no legacy names to break** because no gate file has ever been successfully written there (hosted evidence). Per-OS on-disk divergence documented in CHANGELOG and a code comment. Rejected alternative: uniform renaming everywhere — gratuitous breakage of existing Unix decks.

**Stage 3 — product P4: directory durability sync (1 hosted failure, real semantics).**
Add `internal/fsutil/sync_windows.go`: `SyncFile` on a **directory** handle returns a documented nil with rationale (Windows `FlushFileBuffers` is invalid on directory handles — hosted proof `verification_test.go:368 Access is denied`; NTFS metadata operations are journaled, and the write-through publications used for coordination files — `MoveFileEx(MOVEFILE_WRITE_THROUGH)` in `lock_windows.go` — already provide synchronous replacement). **File-handle fsync stays mandatory and unchanged.** This is a disclosed, reviewed durability-semantics decision (slightly weaker than Unix dir-fsync for crash-window durability of directory entries), to be recorded in FINAL Known risks and CHANGELOG — never a silent skip. Rejected: volume-handle flush (requires privileges end users won't have).

**Stage 4 — product P3: coordination-file opens under Windows sharing semantics (11 failures).**
Diagnose before fixing: add a one-cycle hosted diagnostic (log the failing open's error class and retry outcome). Candidates: transient third-party handles (Defender/indexer on freshly created files under `AppData`) vs a structural window in our own publication (temp-file handle vs concurrent reader). Fix shape depending on evidence: (a) bounded retry — only on `ERROR_SHARING_VIOLATION`, only for these read/open operations (lock file open, `lock-origin` read), small bound (~250 ms), and the full identity/exclusion verification re-runs after success so no check is bypassed; or (b) structural reorder if our own code holds the conflicting handle. The adversarial rename-root tests (`snapshot_read_test.go:261/:432`) are a different sub-problem: on Windows you cannot rename a directory out from under an open `os.Root` — the test's mutation must be redesigned (e.g. swap a file inside the root) so the same product guarantee ("materialroot changed ⇒ refuse") is still exercised for real. No assertion dropped.

## Risks

1. **Privacy regression** — the platform split must keep Unix semantics byte-identical (gated by darwin+ubuntu legs) and Windows acceptance must fail closed on unreadable/non-ACL volumes; an over-broad allow-list would ship weaker privacy — the exact thing the prompt forbids. Refutation tests (hostile ACL fixtures) belong in the acceptance criteria.
