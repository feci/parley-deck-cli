The coordinator role does not use dsh's model loop (`turn/start → agent/request → llm/stream`) because participants are foreign CLIs writing files; it does not use `tools/pre-execute` policy because tool calls are handled by each agent's own harness; it does not use `ctx.skills` discovery (parley's skills live in `~/.hermes/skills/`, not a dsh profile); it does not use `ctx.sessions` event durability for artifacts because artifacts must survive any runtime (git-tracked `.md`, not session events). "More composable" is not enough — zcode-1 is correct that we'd be using a harness as a task runner.

Counter I must answer directly: dsh does ship `subagent-claude-code` and `subagent-codex` (PRIMARY: zcode-1.md §1, confirmed against `packages/subagent/` refs in zcode-1 and claude-1). They run the real products as foreign processes — the exact shape needed. Why inherit them? They are one-shot/non-resumable (zcode-1.md: "fresh process, non-interactive by design, no follow-up, no progress streaming, no persona"), pin private payloads (`@openai/codex@0.147.0`; Claude SDK 0.3.220 / CLI 2.1.220 — not the host binary), inherit parent cwd but not conversation, and are excluded from the production closure (SECONDARY: zcode-1.md provider note + production-exclusion note). Two of six harnesses covered, and each is frozen by dsh's release cadence — the owner's `CHANGELOG.md` shows active six-adapter maintenance (`zcode` adapter 1.45.0, `procctl` seatbelt fix 1.46.0). Inheriting these providers trades a live, cross-platform Go adapter family for a pinned RC payload. That is a loss, not a win.

The genuinely attractive primitives (SECONDARY: zcode-1.md §2 mapping + claude-1.md §2; I did not verify `docs/architecture.md` live — only tarball + cited docs): `ctx.subagents` named providers, `ctx.sessions.fork()`, and especially the "model-visible means logged" invariant (`SessionEventMap`, `ignorable: true`). I agree with zcode-1 (§6 condition) that the right borrow is the *idea*, not the dependency: adopt the named-provider registry and the model-visible-logging invariant inside parley's adapter layer, not as a rebuild onto a preview runtime.

Operational reliability as a selection criterion
Yes, it changes the design. PRIMARY (RECALL): `opencode-1` failed twice (claude-1.md inbox note; zcode-1.md §3 notes opencode-1's trajectory — skeleton only in round 1). The audit's own `FINAL.md` (§3) records this as a harness-level reliability failure (like hermes-1's three lost analyses). Design implication: a harness that reliably dies mid-task should not be the sole authority for any round; the design should require at least two independent harness stacks for any binding verdict, and a provider that cannot survive long sessions should be assigned bounded slices (zcode-1.md §3 suggestion — adopted). A dsh plugin using `subagent-claude-code`/`subagent-codex` as one-shot providers would lose the very reliability guard (independent harness + durable file artifacts) that the audit proved load-bearing.

Current recommendation: WAIT (closer to DON'T) — do not rebuild; do not bind to 0.1.1-rc.2; adopt zcode-1's change-condition (tagged stable release + six-provider parity + kill/artifact/drift/mutation parity). Borrow the named-provider registry and model-visible-logging ideas into the Go adapter layer, not as a dsh dependency.
