## Summary

**PRIMARY — Recommendation in one sentence.** Choose **PLUGIN-ALONGSIDE**: make a pinned `dsh` bundle an optional interaction, scoped-tool, and native-harness-launch layer, while the Go CLI remains the deterministic protocol kernel and artifact authority. This conclusion follows from the current DeepSeek Harness source, the Cordis lifecycle source, and the controlled six-harness audit in this repository; it is not a judgment about the DeepSeek model.

**PRIMARY — Why.** `dsh` has real architectural value: per-agent tool scopes, monotonic tool denial, dynamic MCP discovery, durable session events, and a first-party subagent seam that already launches real Codex and Claude Code processes. It does **not** presently replace Parley's cross-restart process attribution, protocol-copy drift guards, file/Git authority model, release matrix, or six independent native harnesses. Sources: [DSH architecture](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md), [extension cookbook](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cookbook/extension-cookbook.md), [subagent subsystem](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/subagent.md), local `internal/procctl/`, local `internal/protocol/drift_test.go`, and `parley-deck/ideas/protocol-and-skill-audit/`.

**PRIMARY — The decisive boundary.** A DSH plugin that calls six LLM APIs through one in-process DSH agent would destroy the measured harness diversity. A DSH plugin that starts the six installed native products as foreign subprocess providers would retain it. DSH's implemented Codex/Claude Code providers prove the latter shape is supported, but only as fresh, one-shot, non-resumable calls today. Source: [implemented Codex and Claude Code backends](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/feature/2026-08-04-claude-code-and-codex-subagent-backends.md).

## 1. How the plugin model really works

**PRIMARY — Boot and mounting.** The phrase “no privileged core” describes the replaceability of harness capabilities, not the absence of bootstrap machinery. `app-boot` creates a root Cordis context and loader, mounts configured entries concurrently, waits for the include graph, and disposes a partially mounted tree on failure. `cordis:group` gives a provider and its consumers one service-isolation realm. Profiles live under `$DSH_HOME` or `~/.dsh`; their ordered bundles and patches compose as bundle rows, profile patch, home patch, then CLI patch. Sources: [app-boot README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/boot/app-boot/README.md) and [architecture](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md).

**PRIMARY — Cordis lifecycle.** A Cordis plugin may be a function, constructor, or object with `apply`; mounting creates a `Fiber` with states including pending, loading, active, failed, unloading, and disposed. Required injected services keep a fiber pending until available; loss of a dependency unloads it and availability can reload it. `ctx.effect()` collects synchronous or asynchronous disposers, and unload runs collected disposers in reverse order. Service publication and event-listener registration are themselves effects, so they are removed with the fiber. Sources: [Cordis registry](https://github.com/cordiverse/cordis/blob/main/packages/core/src/registry.ts), [Fiber](https://github.com/cordiverse/cordis/blob/main/packages/core/src/fiber.ts), [reflection/service access](https://github.com/cordiverse/cordis/blob/main/packages/core/src/reflect.ts), and [events](https://github.com/cordiverse/cordis/blob/main/packages/core/src/events.ts).

**PRIMARY — What “reversible effects” really guarantees.** It guarantees lifecycle reversal only for effects the plugin registers with a correct disposer: services, listeners, timers, registrations, connections, or owned processes can be unwound. It is not a transaction over the outside world. Files already edited, Git commits, network mutations, and tools run by a foreign agent remain changed unless the plugin implements explicit compensation. The DSH Codex/Claude implementation note says those providers do not roll back tool or file side effects. Sources: Cordis `fiber.ts` above and the [implemented provider note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/feature/2026-08-04-claude-code-and-codex-subagent-backends.md).

**PRIMARY — Foreign processes.** A plugin can make process ownership reversible by spawning through an effect and returning a disposer that terminates and waits for the process tree. DSH's shared subprocess layer is used by the Codex/Claude providers for whole-tree termination while the operation is live. That is not evidence of Parley-style durable kill after the harness itself restarts: the provider operation is parent-scoped, fresh, and non-resumable, and I found no persisted boot ID/start-time/process-group attribution contract in the inspected DSH sources. Sources: the implemented provider note and local `internal/procctl/procctl.go` for the stronger Parley contract.

**PRIMARY — Isolation is scoped dependency resolution, not a security boundary.** Cordis's context proxy restricts undeclared context-service access and isolate realms separate service resolution. A plugin is still JavaScript executing in the DSH Node process and can use ambient Node capabilities unless an OS sandbox separately confines it. DSH exposes `ctx.sandbox`, `ctx.shell`, and `ctx.subprocess` as distinct capability seams; the isolate realm itself is not an OS process, container, or filesystem sandbox. Sources: Cordis `reflect.ts`, [app-boot README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/boot/app-boot/README.md), and [DSH architecture](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md).

**PRIMARY — Reach.** A declared plugin can register or replace services, typed events, tools, agent presets/loops, prompts, session events, jobs, commands, UI, filesystem and subprocess behavior exposed through the context; the architecture explicitly describes every major harness capability as a plugin seam. That flexibility also means a Parley bundle loaded at root scope can affect every session in the profile unless it deliberately registers inside a narrower agent context. Sources: DSH architecture and [tool registry source](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/tools/src/index.ts).

**PRIMARY — Hot reload.** The loader transactionally recomposes on HMR and keeps the last-good tree when an update is rejected. This protects in-process composition; it does not undo external side effects made before a disposer or compensation succeeds. Source: [app-boot README](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/boot/app-boot/README.md).

**PRIMARY — Packaging and versioning.** A bundle is an npm package whose `package.json` points `dsh.bundle` at a patch; a profile package declares dependencies and an ordered `dsh.profile` bundle list. `dsh plugin` delegates package operations to pnpm. Git-installed packages can execute author-supplied `prepare` code outside the harness sandbox, so the official guide advises pinning a commit. I found ordinary npm/package dependency versioning and runtime load validation, but no declared stable DSH plugin-API compatibility version in the inspected manifest contract. Source: [publishing guide](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/publish.md).

**PRIMARY — Current maturity.** The upstream README calls the project a developer preview and warns of compatibility-breaking changes. The inspected CLI package is `@deepseek-ai/dsh` `0.1.1-rc.2`; the workspace requires Node `^22.19.0 || >=24.0.0` and uses pnpm `11.7.0`. Sources: [repository README](https://github.com/deepseek-ai/deepseek-harness), [CLI package.json](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/package.json), [root package.json](https://github.com/deepseek-ai/deepseek-harness/blob/master/package.json), and [development guide](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/development.md).

## 3. Harness diversity: worth keeping, or does it collapse?

**PRIMARY — The controlled record says keep it.** In `protocol-and-skill-audit`, the original corpus had 47 findings. The final adjudication counted 36 confirmed corpus findings plus one supplemental measurement; the confirmed corpus decomposed as Codex 23, Zcode 7, Kimi 4, and Claude 2. This is direct evidence that the harnesses did not behave as interchangeable wrappers around models. Sources: local `parley-deck/ideas/protocol-and-skill-audit/FINAL.md`, `round-01/*.md`, `round-02/*.md`, and signoffs.

**PRIMARY — Codex's behavior was distinct.** Codex filed 24 findings, including executable probes against gates and state machines; 23 met the final “at least one confirmation and no refutation” criterion. Its round-2 additional verification found standalone preflight selecting installed adapters rather than the canonical roster, a miss outside the assigned finding matrix. Source: local `round-01/codex-1.md`, `round-02/codex-1.md`, and final ledger.

**PRIMARY — Kimi and Zcode were distinct in another direction.** Kimi independently found the managed-core `doctor` integrity hole and `sync-project` deleting `protocolRole`; Zcode independently rebuilt Codex's temporary probes from scratch because the original probe files correctly did not exist in the shared tree. Zcode's later signoffs mechanically re-derived every ledger number and caught repeated off-by-one and commit-attribution errors. Sources: local `round-01/kimi-1.md`, `round-02/kimi-1.md`, `round-02/zcode-1.md`, and `signoff-zcode-1.md`.

**PRIMARY — Hermes exposed a harness reliability failure, not random noise.** Claude's round-2 method note records that Hermes produced three complete analyses and lost them, succeeding on the fourth attempt only after the task was reduced and the file was written incrementally. The final review record also says the same participant supplied PRIMARY-tagged evidence that failed execution twice: seven earlier tie-break verdicts were discarded, and a later claimed mutation-test failure was false even though it accidentally pointed at a real coverage hole. Sources: local `round-02/claude-1.md`, `review/consensus.md`, and `FINAL.md`.

**PRIMARY — OpenCode's trajectory was different again.** Its design round-1 artifact was only the required skeleton, but its later tightly bounded review slice gave a useful per-test finding that no existing assertion had been weakened. That is evidence for assigning harness-shaped slices, not for assuming identical endurance or breadth. Sources: local `round-01/opencode-1.md` and `review/round-01/opencode-1.md`.

**PRIMARY — Agreement was not the valuable signal.** Kimi and Zcode confirmed 66 of 74 findings they assessed, about 89%, while all nine REFUTED verdicts in the main corpus came from Codex. The audit closed only after reviewers re-derived counts and mutation-tested fixes rather than accepting consensus prose. Source: local `protocol-and-skill-audit/FINAL.md` and final signoffs.

**PRIMARY — DSH can preserve this only through native foreign providers.** Its `ctx.subagents` service supports coexisting named providers, and first-party `codex` and `claude-code` providers start the real product process with native login/config/settings retained. Each call is currently fresh, one-shot, non-resumable, inherits the parent working directory rather than conversation, and has no progress/follow-up/human-interaction channel. This preserves harness behavior better than six DSH presets, but it does not yet cover the other four products or long-session recovery. Sources: subagent subsystem and implemented provider note.

**PRIMARY — Design consequence.** A safe DSH bundle should treat `claude-code`, `codex`, `hermes`, `kimi`, `opencode`, and `zcode` as six provider implementations behind `ctx.subagents`, hand each a complete artifact-writing task, and validate the resulting file with the Go kernel. It should not translate them into six `ctx.llm` model adapters or force their tool calls through one shared DSH loop. This is an inference from the controlled local audit and the provider source above.

## 4. What we would lose

**PRIMARY — Runtime/install simplicity.** The shipped Parley command is a Go executable and runs without Node after it is built. The local development installer builds/copies it; the Homebrew formula builds with Go at install time, so “no runtime” is true of the resulting executable, not of every installation route. DSH requires a supported Node runtime, and profile/plugin changes use npm/pnpm resolution. Sources: local `README.md`, `scripts/install-local.sh`, `../homebrew-parley/Formula/parley-deck-cli.rb`, and DSH development/publishing docs.

**PRIMARY — Offline operation.** An already installed DSH profile can run without re-downloading its JavaScript packages, so “Node means no offline use” would be too strong. The regression is that a working Parley install now depends on a compatible Node runtime and resolved profile dependency tree, while the Go kernel's local status, validation, artifact, and process-control commands need only the executable. Neither design makes hosted model calls offline. Sources: local CLI source/install docs and DSH profile/plugin docs.

**PRIMARY — Durable process safety.** Parley persists PID, PGID, boot ID, process start identity, command, marker, and timestamp; restart-time kill fails closed unless the live process matches every recorded identity facet. Unix starts a new session and kills the process group with TERM then KILL; macOS uses kernel boot time plus microsecond process start, Linux uses `/proc`; Windows explicitly lacks durable cross-restart attribution and uses best-effort `taskkill /T /F` only for the live path. DSH's inspected provider lifecycle terminates an owned live tree but does not match this persisted attribution contract. Sources: local `internal/procctl/procctl*.go` and DSH implemented provider note.

**PRIMARY — Drift guards.** `internal/protocol/drift_test.go` fails closed if the embedded bootstrap protocol and live deck differ outside five explicit project zones; it also checks structural anchors, bootstrap placeholders, generated table signatures, and sibling skill surfaces when available. Rebuilding as a plugin would require deliberately porting these guards and their cross-repository tests; Cordis HMR's last-good composition is not equivalent. Source: local `internal/protocol/drift_test.go`.

**PRIMARY — Release and platform work.** Local release evidence shows separate, independently checked routes: Homebrew formulae for CLI and skill; GitHub release assets for CLI and skill; WinGet manifests for CLI and skill; and npm for the skill. The current local formulae are CLI `1.46.0` and skill `2.10.0`; the checked-in WinGet fork currently reaches CLI `1.45.0` and skill `2.9.0`; npm search reports skill `2.10.0`. Replacing the CLI with a DSH package would retire neither the skill's Windows portable/WinGet users nor the independent channel checks automatically. Sources: `../homebrew-parley/Formula/`, `../winget-pkgs/manifests/f/Feci/`, [npm result for `parley-deck-skill`](https://www.npmjs.com/search?page=1&perPage=20&q=keywords%3Aagent-skill), and local `parley-deck/ideas/roster-operations-standard/deploy-verification/hermes-1.md`.

**PRIMARY — The brief's “six channels” count does not reproduce.** Counting channel families gives four: npm, GitHub releases, Homebrew, and WinGet. Counting product-by-channel routes visible in the local release record gives seven: three CLI routes (GitHub, Homebrew, WinGet) and four skill routes (npm, GitHub, Homebrew, WinGet). `scripts/install-local.sh` is an additional development/install route, not a published channel. I would not base a migration estimate on “six” until the owner defines what is being counted. Sources: the formulae, WinGet manifests, npm result, and local deploy-verification record above.

**PRIMARY — CI evidence is asymmetric.** The CLI checkout has no `.github/` directory at HEAD (`git ls-tree -r --name-only HEAD .github` returned no paths), so I could not inspect the CLI release workflow the brief expected. The sibling skill repo does have `.github/workflows/release-portable.yml`, which runs Node 24, Python 3.10, `npm test`, builds Windows portable binaries, and uploads them on release publication. Source: exact local commands and `../parley-deck-skill/.github/workflows/release-portable.yml`.

**PRIMARY — Maturity risk.** Moving the authority into DSH now would couple Parley's compatibility promise to a developer-preview `0.1.1-rc.2` host whose own README permits breaking changes. An optional pinned bundle contains that risk; a rebuild inherits it. Sources: upstream README/package files.

## 5. The tool-plugin question (MCP/mcpanywhere, graphify, openviking, cognee)

**PRIMARY — `ctx.tools` is more than a different config file.** Tool registrations are scoped and disposable; a narrower agent scope can shadow inherited tools, `restrict()` intersects visible inherited sets, ToolSearch can progressively disclose them, and `tools.guard` supplies a final monotonic denial after pre-execute hooks. That is a genuine improvement over making every gateway tool visible to every agent. Source: [tool registry source](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/tools/src/index.ts) and [extension cookbook](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cookbook/extension-cookbook.md).

**PRIMARY — DSH's generic MCP client is already substantial.** It mounts one plugin per server over stdio or Streamable HTTP, discovers paginated tool lists, assigns deterministic names, registers a new generation transactionally, retains the previous generation if refresh fails, propagates abort/timeout, and disposes the connection and registrations with the plugin. Sources: [MCP client](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/mcp/mcp-client/src/index.ts) and [MCP tool synchronization](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/mcp/mcp-client/src/tools.ts).

**PRIMARY — `mcp-anywhere`.** This machine's canonical configuration connects the gateway over stdio with `docker exec -i mcp-anywhere-app mcp-anywhere connect`; it aggregates tools from all active server containers and has no per-user filtering. DSH could mount that gateway as one MCP server, then use agent-scoped restrictions and ToolSearch to reduce exposure. The transport and underlying tools would be the same; the improvement would be lifecycle, namespacing, visibility, and policy at the harness edge. Source: `/Users/tomasfecko/.codex/AGENTS.md` read this session plus DSH MCP/tool sources.

**PRIMARY — Do not duplicate the gateway first.** The lowest-risk experiment is a bundle row configuring the existing `mcp-anywhere` stdio command and a Parley-specific tool visibility policy. Native plugins are justified only when lifecycle hooks add something MCP cannot express, such as automatic phase receipts or validated session capture. This is an inference from the local gateway contract and DSH MCP implementation.

**PRIMARY — Graphify.** This repository already has `graphify-out/graph.json`. The ratified local evaluation keeps Graphify as an advisory code/doc navigation and audit tool, never as the selector of normative protocol or participant objections; its exact-symbol navigation was useful, while semantic traversal did not prove completeness. A DSH wrapper can improve discoverability and scope, but it cannot turn graph retrieval into proof that omitted rules do not exist. Sources: local `parley-deck/ideas/speedup-tooling-evaluation/FINAL.md` and `round-01/codex-1.md`.

**PRIMARY — OpenViking.** OpenViking already exposes a native HTTP MCP endpoint and tool surface for search, recall, read/list, remember, resources, and deletion; direct MCP is explicitly described as a pure model-invoked tool surface without automatic recall or capture. Therefore DSH's generic MCP client is sufficient for a first integration. A native DSH plugin would only be materially different if it used session hooks for automatic capture/recall, which would need a Parley-specific proof that it cannot hide or replace canonical evidence. Source: [OpenViking MCP guide](https://github.com/volcengine/OpenViking/blob/main/docs/en/guides/06-mcp-integration.md) and [capability reference](https://github.com/volcengine/OpenViking/blob/main/docs/en/agent-integrations/16-capability-reference.md).

**PRIMARY — Cognee.** Cognee already supplies an MCP server over stdio, SSE, or HTTP with `remember`, `recall`, and `forget`, plus dataset/workspace tools. The local Parley evaluation rejected Cognee as a normative context selector because this deck's measured problem is over-transmission, not missing memory, and because retrieval cannot prove that no objection was dropped. DSH makes the optional tools easier to scope; it does not change that trust result. Sources: [Cognee MCP README](https://github.com/topoteretes/cognee/blob/main/cognee-mcp/README.md) and local `parley-deck/ideas/speedup-tooling-evaluation/FINAL.md`.

**PRIMARY — Policy boundary.** Graphify, OpenViking, Cognee, and ToolSearch may propose, locate, or audit. None should decide which protocol rules, round artifacts, objections, or signoffs reach a participant, and none should calculate quorum. The canonical files and deterministic Go validators must remain authoritative in the first plugin. Source: the ratified local tooling evaluation and the controlled audit's repeated finding that a printed rule binds only where its gate runs.

## 6. Recommendation

**PRIMARY — PLUGIN-ALONGSIDE.** Keep `parley` as the source-of-truth executable. Build, in a later implementation idea, a small pinned DSH bundle that: (1) exposes selected Go CLI operations as guarded tools; (2) connects the existing `mcp-anywhere` gateway; (3) applies scoped ToolSearch/restrictions per phase and participant; (4) uses the real Codex/Claude providers and prototypes equivalent foreign providers for Hermes, Kimi, OpenCode, and Zcode; and (5) logs receipts into DSH sessions while leaving canonical artifacts, quorum, drift checks, and process attribution in Go. This is an architectural recommendation derived from all PRIMARY sources above, not an implementation performed in this study.

**PRIMARY — Why not REBUILD.** A rebuild would presently trade a stable deterministic kernel for an RC host, collapse or reimplement the release/process/drift machinery, and either lose four native harnesses or require provider work before parity can even be measured. The bundle-alongside experiment captures DSH's real gains without making those losses irreversible. Sources: current DSH maturity/package source, local audit, and local safeguards.

**PRIMARY — Condition that would change my mind.** Change to **REBUILD** only after a pinned non-preview DSH release and a parity prototype pass one controlled gate: all six native products run as native harness processes; restart-time kill is at least as fail-closed as `procctl`; artifact, quorum, §15, and drift mutation tests remain red when their fixes are reverted; offline local validation still works after installation; and the actual release-route matrix is reproduced on macOS, Linux, and Windows. A failed item keeps the Go kernel; a passed gate makes a port evidence-based rather than aspirational.
