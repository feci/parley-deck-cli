## Summary

`dsh` is a Node/TypeScript developer-preview harness (0.1.1-rc.2 at PRIMARY verify) built on Cordis (`@deepseek-ai/cordis ^4.0.1`) where everything is a plugin mounted to a shared `ctx`. It is real, installable (`npm info` and `npm pack` succeeded in `/tmp/dsh-verify`), and documented at `docs/architecture.md` / `docs/development.md` / `AGENTS.md`. The brief is broadly right about Cordis services (`core/session`, `llm/llm`, `core/agent`, `core/agent-loop`) and about bundles/profiles (`dsh.profile` / `dsh.bundle` in `package.json`; confirmed from the tarball's `package.json`). It understates one risk: the npm package distributes only compiled `.js` bundles (`lib/plugin-*.js`, `lib/bin.js`, 20 files, 33.7 kB tarball) — there is almost no visible source to inspect, so "plugin isolation" must be taken on the framework's contract, not verified by reading a plugin's code.

The audit (`protocol-and-skill-audit`) proves harness diversity matters: six agents produced measurably different results (codex-1 6/8/9 verification split; kimi-1 36/6; zcode-1 30/2; the ledger itself had three arithmetic errors corrected; two fabricated-PRIMARY signoffs discarded per `FINAL.md`). Collapsing to "one harness, six models" loses that.

Recommendation: WAIT. The preview is too young (breaking-changes flagged in README/docs), the package surface is opaque (only compiled JS), and parley-deck's durable-kill (`procctl`), drift guard (`drift_test.go`), cross-platform releases, and six delivery channels have no equivalent in `dsh`. Change my mind when `dsh` reaches a stable non-preview release with readable plugin source, a durable-session persistence spec, and a documented process-control/sandbox model.

## 1. How the plugin model really works

PRIMARY: `npm info @deepseek-ai/dsh version` → `0.1.1-rc.2` (2026-08-26). `npm pack @deepseek-ai/dsh` produced `/tmp/dsh-verify/deepseek-ai-dsh-0.1.1-rc.2.tgz` (33.7 kB, 20 files). Extracted `package/package.json`: `"type":"module"`, `"bin":{"dsh":"lib/bin.js"}`, `dependencies` list 43 `@deepseek-ai/*` plugin packages (`dsh-base ^0.1.1-rc.2`, `dsh-skill ^0.1.1-rc.2`, `dsh-mcp-client`, `dsh-subagent`, `dsh-cordis-client-runner`, etc.) plus `@deepseek-ai/cordis ^4.0.1`. No source files in the tarball other than `config/agent-presets/*.yml`, `config/agent-presets/*/*.md`, and the compiled `lib/*.js`. That matches the brief's "everything is a plugin" claim (SECONDARY from brief line 33): `core/session`, `core/system-prompt`, `core/tools` (`ctx.tools`), `core/agent` (`ctx.agents`), `core/agent-loop` (`ctx.agentLoop`), `llm/llm` (`ctx.llm`) are the service keys.

SECONDARY (brief lines 31-46; docs at `https://github.com/deepseek-ai/deepseek-harness` linked): Cordis framework (`github.com/cordiverse/cordis`) powers plugin mounting/unmounting; bundles declare via `dsh.profile` (profile bundles) and `dsh.bundle` (bundle patch file) in `package.json`; profiles kept in Harness home; composition order bundles → profile `cordis.patch.yml` → home patch → CLI `--patch`; inspectable via `dsh --profile web --dump-config`. The loop: `turn/start → agent/pre-step (waterfall) → step/start → agent/request → llm/stream → assistant/message → tool/call → tools/pre-execute → tools/execute → tools/post-execute → step/end → agent/turn-stopping (serial) → turn/end`. Durable session events (`turn/*`, `step/*`, `user/message`, `assistant/*`, `tool/*`) survive reload; `ctx.sessions.fork(source, boundary?, childSessionId?)` exists.

PRIMARY (correction to brief): the brief says "There is no privileged core" (line 34). That is *architecturally* true in Cordis (SECONDARY: docs/architecture.md link reads "Every part of the product is a plugin, including the model adapter... There is no privileged core to patch: you extend dsh by mounting a plugin beside the others"). But in practice, the npm package's `dsh` binary ships with a *hard-coded* plugin tree (43 dependencies pinned at exact `^0.1.1-rc.2` ranges). You cannot inspect the plugin source from the installed package; you must clone the repo (`git clone https://github.com/deepseek-ai/deepseek-harness`) and build (`pnpm install`, `pnpm run build`). That is a different isolation model than "read the installed plugin file": it requires source-level access. I did NOT clone the full repo (would exceed session scope); I note it unverified.

"Reversible effects" (SECONDARY from docs link / brief line 33): Cordis effects unwind when the plugin unloads — service registrations are removed from `ctx`, event listeners unmounted, session mutations rolled back to the last boundary. PRIMARY partial: `npm pack` shows `dsh-cordis-plugin-loader ^1.0.2` and `dsh-cordis-plugin-include ^1.0.6` — loader and include plugins exist — but I could not verify the unwind mechanism without reading the framework source (not in tarball). For a plugin that shells out to a foreign process (e.g. `claude-code` CLI or `zcode` binary): the harness's `core/subprocess` / `core/agent` service can spawn (SECONDARY: docs/architecture.md table: "Add shell execution → register `ctx.shell` backend; local one spawns through `ctx.subprocess`"). A reversible *Cordis* effect (remove the service) does NOT kill the foreign process automatically — the brief's "durable session events survive reload" is about event logs, not OS processes. That is an important gap: `procctl` (PRIMARY read below) handles durable kill explicitly; `dsh` has no equivalent mechanism in the package I inspected.

## 5. The tool-plugin question (MCP/mcpanywhere, graphify, openviking, cognee)

PRIMARY: `npm pack` shows `dsh-mcp-client ^0.1.1-rc.2` in dependencies. The docs link (`docs/architecture.md`, SECONDARY) states: "Plugins provide every agent capability, including ... skills, sessions, sandboxes, storage, loops, scheduling, and the UI" and specifically: "Add model-facing capability → register on `ctx.tools`; its schema joins prompt assembly"; "Add filesystem access or policy → register a `ctx.fs` provider or listen to `fs/*` events". `dsh-tool-*` packages (`dsh-tool-fs-search`, `dsh-tool-subagent`, `dsh-tool-fs`, `dsh-tool-bash-persistent`) confirm tool registration exists.

Does `ctx.tools` make `mcpanywhere` / `graphify` / `openviking` / `cognee` genuinely better than existing MCP wiring?
- `mcpanywhere`: `dsh-mcp-client` is present in the tarball. It likely provides MCP tool discovery (SECONDARY: package name implies it). A plugin that registers `mcpanywhere` tools on `ctx.tools` would be a native integration — the harness's prompt-assembly mechanism (`agent/request → llm/stream`) would see the tools directly, rather than relying on an external MCP bridge. PRIMARY partial: the tarball contains compiled `.js`; I could not verify the exact tool-registration API without reading source. SECONDARY: docs link confirms `ctx.tools` registration.
- `graphify` / `openviking` / `cognee`: SECONDARY: the brief references these (line 24-25); no packages named `graphify` or `cognee` appear in the `dsh` dependency list. These are likely user-specific plugins. A `dsh` plugin could register them as `ctx.fs` providers or `ctx.tools` — the mechanism exists — but the value depends on whether the plugin's effect is reversible and durable. PRIMARY: `dsh`'s durable session events (`turn/*`, `step/*`) survive reload (`SECONDARY` from docs link). If `graphify` writes to `ctx.fs`, the write would be durable; if it only produces a `tool/result` message, it survives as an event but may not persist to a file unless `dsh-fs-local` (present) handles persistence.
- The key difference: `dsh`'s `ctx.tools` integrates with the harness loop (step/turn events) natively; an external MCP server requires a separate process (`dsh-mcp-client`) that bridges between the harness and the server. A native `ctx.tools` plugin avoids that bridge overhead and gains event-level durability. PRIMARY: `npm pack` includes `dsh-tool-subagent`, `dsh-subagent`, `dsh-subagent-control` — subagent spawning is native, not external. That supports the claim that native plugins are more tightly coupled.
- Caveat: without reading the compiled `.js` or the repo source, I cannot verify whether the `reversible effects` contract holds for a `graphify` plugin that writes to `ctx.fs`. I note it unverified (see "What I could not verify").

## 6. Recommendation
