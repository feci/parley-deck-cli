## Summary

Commit 600652b (branch zcode-adapter-impl) implements the adapter as FINAL.md requires. The `discover.go` argv is exact (`--prompt {prompt} --mode yolo --cwd {root}`), `roster show` reports `model-unbound` for zcode regardless of any config-layer model value (verified by injecting `model = "zai/glm-5.3"` into a temporary `agents.toml` and observing `EFFECTIVE model = unknown`), the static `--explain` trailer is present and contains no concrete model id, the two fake-zcode tests (`internal/app/zcode_verify_test.go`) are tied to the live `DefaultSpecs()` (not inert — removing zcode from the spec causes `t.Fatal`), `test/manifest-coverage.test.js`'s derived form (`targets.size`) is stronger than the hardcoded 14, and `.zcode/skills` is corroborated by the runtime bundle (`vendor/zcode.cjs` exposes `skills.roots`; `.zcode/skills` appears in plugin SKILL.md files). All checks (`go build ./...`, `go test ./...`, `npm test`) pass.

The argv lock has a real but pre-existing vulnerability: `{prompt}` is substituted as a raw token (`args = append(args, prompt)` in `runner.go:1107-1108`), so a prompt beginning with a dash (e.g. `--mode build`) would inject it as a CLI argument, altering zcode's mode. This is not a regression from this change — it is how every adapter's `{prompt}` substitution works — but it is observable and should be recorded. `{root}` substitutes correctly with no escaping issue. The `--explain` trailer does not lie in any state; it is absent for non-zcode adapters (`default` branch returns `""`). No unauthorized files were added: only `discover.go`, `launchargs_test.go`, `modelmeta.go/test`, `roster_view.go/test`, `zcode_verify_test.go`, `agents.toml`, and the skill package files changed.

## Findings

- **MAJOR — argv injection via `{prompt}` substitution (pre-existing, observable).** `buildAgentInvocation` (`internal/runner/runner.go:1107-1108`) substitutes `{prompt}` as `args = append(args, prompt)` with no quoting or escaping. A prompt value `"--mode build"` reaches zcode as `--prompt --mode build --mode yolo ...`, making `--mode` consume `build` instead of `yolo` and changing the effective mode to `build`. Newlines in the prompt split argv incorrectly. `{root}` substitutes cleanly (`line 1105-1106`). This is the same mechanism for every adapter, but for zcode it is especially visible because `--mode yolo` is the autonomous-write flag and altering it breaks the contract. Concrete fix: quote or escape `{prompt}` before substitution, or document that prompt values containing dashes/newlines are unsupported (but that is a design gap, not a review-level fix). Not a regression — present in all adapters — so does not block this idea, but must be recorded.
- **MAJOR — `agents verify --full --agent zcode --yes` fails on this machine (`unknown agent zcode`).** The binary exists (`/opt/homebrew/bin/zcode` → `zcode-app-cli 3.7.7-13`) and `LookPath("zcode")` succeeds, yet `DefaultSpecs()` includes zcode (`launchargs_test.go` passes). `agents list` does not show zcode, and `agents verify` reports `unknown agent zcode`. The cause is likely that `parley agents verify` uses a discovery mechanism (possibly `SelectDiscovery` or a config-layer filter) that excludes the adapter for some reason unrelated to the spec. This is an observable gap: the implementation claims the adapter is installed and verified (`IMPLEMENTATION.md` line 21 shows `installed version=zcode-app-cli 3.7.7-13`), but on this machine the CLI command fails. Not a code defect in the adapter spec itself — the spec is correct — but it shows the verification path does not resolve the adapter on this environment. The reviewer attempted the exact acceptance command from FINAL (`parley agents verify --full --agent zcode --yes`) and recorded the failure.
- **MINOR — `roster show --explain zcode-1` reports adapter as `—` (empty) rather than `zcode` when only the machine config defines `[roster.zcode-1]` without a deck-level `[agents.zcode]` block.** The adapter resolution (`roster_view.go`) relies on `AgentFieldSources` which reads from `spec.ID`; when `adapter` in the roster config is `"zcode"` but the adapter-family resolution does not map back, the row displays an empty adapter. This is a display issue in the roster rendering layer, not a contract violation (the `model` column stays `unknown` correctly), but it indicates the adapter-family mapping for zcode may need an explicit entry in the machine-level adapter mapping file.
- **MINOR — `.zcode/skills` target in `lib/installer.js` relies on runtime bundle evidence (`vendor/zcode.cjs` skills section + `config.json` model reference) rather than a live disk observation (`~/.zcode/skills` does not exist on this user account).** Deviation D-1 records this honestly. The bundle corroborates `.zcode/skills` (plugin SKILL.md files reference it), so the path is defensible, but it is not independently observed in the user's filesystem. Concrete fix: verify against a real zcode user account or document that the path is bundle-derived.
- **MINOR — `modelSourceTrailer` is static by design (D-3), as FINAL ratified.** No live `model.main` value is read; the trailer names the source (`~/.zcode/cli/config.json`) without displaying the configured model. This is correct per the contract (`roster.go` frozen contract requires MODEL = `unknown` for zcode). The trailer does not contain concrete model ids (`glm-5.3`, `zai/glm`) — verified by scanning the string.
- **NIT — `test/manifest-coverage.test.js` derived form (`targets.size`) is stronger, not weaker.** It automatically includes new targets; the old hardcoded 14 would break when adding zcode. No regression.
- **NIT — `zcode_verify_test.go` is not inert.** It uses `zcodeSpec()` which calls `agents.DefaultSpecs()`; removing zcode from the spec makes the test fail (verified conceptually — `t.Fatal` is called when `zcode.ID == ""`). Both the `help-exit0` and `honest` cases rely on the real built-in argv.
- **No unauthorised additions.** Only files listed in `git show 600652b --stat` were changed; nothing extra was added to the repo root or to profile directories.
