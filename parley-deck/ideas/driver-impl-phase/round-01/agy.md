## Summary
The proposed driver extension to support Phases 5–8 is protocol-compliant, but requires additional safety mechanisms and strict role enforcement to protect the user's workspace. While `--auto` is acceptable for writing markdown design artifacts, code modification requires an explicit, separate opt-in (e.g., `--allow-code-writes`). The proposed boundary of halting at "ready to merge" is correct, but additional guards must ensure git working directory safety and handle loop termination/escalation gracefully.

## Proposed approach
- **Explicit Safety Gate**: The driver must require an additional explicit CLI flag (e.g., `--allow-code-writes` or `--auto-implement`) to execute Phase 5 (implementation) and Phase 8 (fix-up). Running `parley run --auto` without this flag must halt before launching code-writing agents, displaying an inbox escalation or terminal instruction.
- **Git Working Tree Safety**: Before running the implementer agent, the driver must verify that the target repository's git status is clean (no unstaged or uncommitted changes). If dirty, it must halt and escalate to prevent destructive overwrites of user work.
- **Strict Role Verification in Rebuild**:
  - The implementer is defined as the author of `FINAL.md` (or specified in `IMPLEMENTATION.md` frontmatter).
  - The driver must dynamically verify that the implementer is excluded from the reviewer pool for Phase 6 review rounds.
  - Review consensus signoffs in `review/consensus.md` must be gathered from all participants (both implementer and reviewers), verifying real per-agent signoffs.
- **Escalation & Circuit Breaking**:
  - If a review consensus file is missing the `outstanding_agreed_fixes` frontmatter or is malformed, the driver must immediately fail closed and log a blocker to the user's inbox.
  - If `MaxFixupCycles` (default 3) is exceeded, or if a build/test failure occurs during implementation or fix-up runs, the driver must halt execution and write a blocking escalation file to the inbox (e.g., `inbox/system-to-user_driver-impl-phase_max-cycles-exceeded.md`).

## Concerns / open questions
- **Write Access & Pushing**: For remote transports like `github-pr` or `gitlab-mr`, opening an implementation PR requires pushing a branch. Does the auto-driver have git push credentials, and how is that write permission verified safely?
- **Build / Test Suite Execution**: How does the driver know if a build or test suite should be executed? Should the driver verify the test results itself, or should it rely entirely on the implementer agent's return status/logs?
- **Idempotency and Re-entry**: If the driver is stopped and resumed, how does it avoid re-running review rounds or fix-ups whose artifacts are already present on disk? The disk-based state detection must be highly robust.

## Risks
- **Destructive Code Modification**: Code-writing agents run commands in the local workspace. A bug in the implementer agent or the generated code could execute destructive operations (`rm -rf`, DB modifications) or run malicious tests. Sandboxing or clear permission boundaries are necessary.
- **Infinite Cycles & Token Exhaustion**: A feedback loop between reviewers and the implementer could spin up to the `MaxFixupCycles` limit over minor or conflicting nits, causing high token usage.
- **Workspace Pollution**: Untracked files generated by builds, test runs, or failed implementation attempts can litter the user's repository and interfere with subsequent steps.
