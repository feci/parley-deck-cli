## Summary

OpenViking's useful idea is the filesystem-sidecar tier (L0 `.abstract.md` ~100 tokens, L1 `.overview.md` ~2000 tokens) per directory, with full L2 loaded on demand. For Parley Deck, this is relevant to the 491 kB / 22-artifact `protocol-generation-bias` bloat (checkable: `ideas/protocol-generation-bias/` ~491 kB) and the lack of cross-idea recall across 41 decks. I adopt **one narrow mechanism only**: a hand-built `.abstract.md` sidecar inside each idea directory (`00-prompt.md` stays canonical; `.abstract.md` is a generated view, never authoritative). The `viking://` URI scheme and md5 identity (`md5(account_id:uri)`) are **out** — zero runtime dependencies, and git SHA + relative path already give stable addressing locally (`COOPERATION.md` §3 layout). The OpenViking plugin (`plugins/memory/openviking/__init__.py`, PRIMARY — file read 2026-08-31) is real but requires an external `openviking-server` (RECALL — docs say `openviking-server doctor` needed); it is not adopted as a dependency.

## Proposed approach

Hand-build, zero new dependencies:

1. **Sidecar `.abstract.md` (L0)** per idea directory. Constraint-forced: `00-prompt.md` must stay the canonical authority per §3 and must stay human-readable with `cat` (§ non-goals). The `.abstract.md` is explicitly a **derived** view (tagged `derives-from:` pointing at `00-prompt.md`), regenerated by the agent that closes the idea (at Phase 4, same agent as `FINAL.md` drafter) or on-demand by `parley context repo-map`. Budget: ~100 tokens, written once per round close, not per participant per round — that avoids multiplying cost (the bloat problem is cross-round artifact accumulation, not per-file size). If a summary is stale: the canonical file (`00-prompt.md`, `consensus.md`, round file) always wins; any agent that acts on `.abstract.md` without confirming against the canonical file is at fault, per the protocol's existing audit-trail rule (§3: "Files are canonical").
2. **No `.overview.md` (L1)**. Constraint-forced: writing 2,000-token summaries for 41 decks × ~22 artifacts ≈ 1.8 M token budget before any adoption measurement. Skip L1 until measurement (§ the user's own requirements) proves the gap is real. The mechanism is named but deferred.
3. **No `viking://` scheme**. Inherited from filesystem layout — git relative paths are already the locator; no new URI scheme required. The md5 identity (`md5(account_id:uri)`) is a server-side key for a vector DB we are not running; the closest local equivalent is `git rev-parse --short HEAD` (locator: shell command) plus the file path, which is exactly what `parley context repo-map --dir .` already emits (checkable in `cmd/parley`; `context` subcommand exists per grep of `internal/app/app.go:218`).
4. **Cross-idea recall mechanism deferred**. The closest existing mechanism: `parley retro` (`internal/app/app.go:144`) scans completed ideas; `parley learn` (`app.go:92`) reads `00-prompt.md` + `FINAL.md`; `parley context repo-map` (`app.go:218`) emits a file listing. None of them index by topic — they index by idea slug. A hand-built `.meta.json` with a `keywords:` array (inherited from `openviking-notes.md` section 3 `.meta.json`) could be added without new dependencies (JSON stdlib), but it costs manual tagging per idea. Defer to measurement (kimi-1's evidence axis).

Trade-off: the sidecar saves ~10–50 tokens of context loading per agent per round (reading `.abstract.md` before `00-prompt.md`) but costs ~100 tokens of author time at close and introduces a stale-summary failure mode. The benefit scales with number of rounds × participants; the cost is fixed per idea. For ideas with ≤2 rounds (`fast` track), the sidecar is likely net negative; for `deliberation` with 5+ rounds (like `protocol-generation-bias` at 3+ rounds today), it is plausibly net positive.

## Concerns / open questions

- Stale `.abstract.md`: the failure mode is concrete. An agent acts on a 3-round-old `.abstract.md` that says "consensus reached — no open items" when a newer `consensus.md` records a `BLOCK`. Mitigation: `.abstract.md` must include `derived-from: 00-prompt.md` and `generated-at-round:` plus a `canonical-file-sha:` reference (inherited mechanism: git SHA locator, see Existing alternatives #3). Any agent must verify against the canonical file before acting; the protocol's audit-trail rule (§3) already requires this. Open: should the CLI enforce it (e.g. `parley learn --verify`) or is the discipline social?
- Cost of writing `.abstract.md`: for `fast` track (≤1 fix-up cycle, ≤3 files) the summary generation cost exceeds likely savings. Constraint-forced solution: only generate `.abstract.md` for `standard` / `deliberation` tracks, and only when round count exceeds 2 (checkable in `00-prompt.md` `status:` field). Inherited decision logic: `COOPERATION.md` §4.0 track selection.
- Integration reality: I (hermes-1) have the plugin installed (`plugins/memory/openviking/__init__.py`: PRIMARY — verified locally 2026-08-31). Adopting the plugin as a runtime dependency violates the zero-new-dependency preference (§ Constraints: "A design that requires running an OpenViking server ... is very likely out of scope"). Not adopted. The mechanism we adopt (sidecar `.abstract.md`) works with `cat` and `grep` independently of the plugin.
- Cross-deck recall is still open. `.abstract.md` per idea helps per-idea recall but does not solve "has any of 41 decks deliberated this?" That requires either `.meta.json` keywords or `parley retro` enhancement — both deferred to measurement. Open question for kimi-1 (evidence axis): what measurement proves the gap exists? Suggest: count unique keywords across 41 `00-prompt.md` files and measure how often `parley learn` returns nothing when a semantic match exists (would require manual labeling; cost is real).

## Risks

- **Stale summary acting as truth** (named failure mode, required): an agent reads `.abstract.md` instead of `00-prompt.md`, takes a wrong action, and the audit trail shows the agent used a derived file. The failure mode is recoverable: `git` preserves the canonical file; the derived file is tagged `derived`; any discrepancy is discoverable by `diff`. The deeper failure — an agent hides behind the summary and ignores contradiction — is a discipline failure, not a mechanism failure. Mitigated by the `derived-from:` and `canonical-file-sha:` tags (constraint-forced from audit-trail rule).
- **Adoption without measurement**: adding `.abstract.md` to 41 existing decks is ~41 × 100 tokens ≈ 4.1 k token cost, plus ongoing maintenance. Without measuring whether agents actually use the summary (e.g. does `.abstract.md` reduce `parley learn` or `parley retro` calls?), the mechanism is ceremony without evidence. Recommendation (not adoption): run a 3-idea pilot (`fast` / `standard` / `deliberation`) with `.abstract.md` and measure usage before fleet-wide adoption. This is consistent with `COOPERATION.md` §4 Phase 5 (`IMPLEMENTATION.md`) measurement practice.
- **Legacy compatibility**: `.abstract.md` is a new file; it does not modify existing artifacts and does not break `cat` / `grep` / `git` (§ Constraints). Backward-compatibility satisfied. Constraint-forced: new file only, no rewrites.
- **English-only violation risk** (§6.6): the `.abstract.md` is in English by convention (same as `00-prompt.md`); no new mechanism introduces non-English text. Constraint-forced by protocol.
