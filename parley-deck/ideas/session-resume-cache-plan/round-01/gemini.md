## Summary

My proposed approach focuses on creating a resilient, cross-agent session resumption capability by treating external agent CLIs as services with discoverable and probeable features. Rather than depending on the internal cache formats of other agents, `parley-deck-cli` will maintain a registry of agent capabilities for session management. This allows for graceful degradation—if an agent supports true session resumption, we use it; if not, we fall back to re-invocation. This balances the goal of a seamless user experience with the reality of interacting with diverse and independently-evolving tools.

## Proposed approach

1.  **Agent Capability Registry:**
    We will create a central file, `~/.parley-deck/agent-registry.json`, to act as a capability manifest for all known agents. This file will store discovered information about each agent's session management features, such as command-line flags for listing, resuming, and forking sessions, as well as known cache locations. This registry becomes the source of truth for *how* Parley interacts with other agents, not *what* is in their caches.

2.  **Discovery and Probing Mechanism:**
    A new command, `parley-deck agents --probe-capabilities`, will be introduced. This command will:
    *   Iterate through known agents (`codex`, `claude`, `gemini`, `hermes`).
    *   Check if the CLI is in the `PATH`.
    *   Parse the output of `help` commands to identify session-related flags (e.g., `--resume`, `--session-id`, `--list-sessions`).
    *   Store these capabilities in the `agent-registry.json`.
    This process makes the system adaptable to changes in external CLIs; re-running the probe can update the registry after an agent CLI is updated.

3.  **Parley Session State Enhancement:**
    The existing `~/.parley-deck/sessions.json` will be augmented. For each Parley run, we will store a mapping between the Parley session and the specific session IDs generated by the participant CLIs during that run.

    *Example `sessions.json` entry:*
    ```json
    {
      "parleyRunId": "20260510T201528.433687000Z",
      "idea": "session-resume-cache-plan",
      "workspace": "/Volumes/My Shared Files/AI_WORKSPACE/parley-deck/parley-deck-cli",
      "lastStatus": "round-01",
      "participantSessions": {
        "codex": { "sessionId": "a1b2-c3d4", "canResume": true },
        "claude": { "sessionId": "claude-xyz-789", "canResume": true },
        "gemini": { "sessionId": null, "canResume": false } 
      }
    }
    ```

4.  **Resumption Workflow:**
    When the user executes `parley-deck-cli --resume <parleyRunId>`:
    a.  `parley-deck-cli` reads its session state from `sessions.json` to get the `participantSessions` map.
    b.  It consults the `agent-registry.json` to find the correct command syntax for resuming a session for each participant.
    c.  For participants with `canResume: true` and a `sessionId`, it constructs and executes the appropriate resume command (e.g., `codex resume a1b2-c3d4`).
    d.  For participants where `canResume` is false or the session ID is null, it falls back to re-invoking the agent with the original prompt for the required step. The UI will indicate this is a "replay" rather than a "resume" for that agent.
    e.  This ensures that the overall Parley workflow can continue even if one or more participants lack a persistent session state, providing a robust and predictable user experience.

## Concerns / open questions

*   **Reliance on Unstable Interfaces:** Parsing CLI `help` text is brittle and susceptible to breakage if an external tool changes its output formatting. Should we encourage a standard agent-level interface (e.g., a `parley-agent-spec.json` file) that CLIs could optionally expose?
*   **Session Context Drift:** If a user manually resumes and interacts with a participant's session outside of a Parley workflow, the state will diverge. Should Parley's session state include a hash or timestamp of the last interaction to detect such drift, or do we consider participant sessions exclusively managed by Parley for the duration of a run?
*   **Handling Auth Failures:** A resume command will fail if the underlying agent CLI requires re-authentication. How do we best detect this specific failure mode and provide a clear message to the user, directing them to re-auth with the correct tool?
*   **Headless vs. Interactive Discrepancy:** Does resuming a session started in a headless context have the same behavior as resuming one started interactively? We must test this for each agent, as discrepancies could lead to unexpected behavior.

## Risks

*   **Upstream CLI Changes:** The primary risk is that an update to a participant's CLI breaks our discovery or resume logic. A versioning scheme in our agent registry, tied to the version of the participant CLI, might be necessary to manage this.
*   **Incomplete State Restoration:** Resuming a CLI session typically restores the conversation history, but may not restore the full context (e.g., working directory, environment variables, previously read files). This could lead to participants behaving inconsistently upon resumption. The design must assume only conversational context is restored.
*   **Security of Discovery:** The probing mechanism must be strictly limited to known CLI tools and their standard help/version commands. Any deeper inspection could have security implications or be perceived as intrusive. We should be fully transparent about what commands are run during the discovery phase.
